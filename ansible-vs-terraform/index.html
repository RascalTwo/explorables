Ansible vs Terraform

When to reach for each, where they win and lose head-to-head, and a flow to decide. Clean-room opinion — the short version: Terraform builds the house, Ansible furnishes & maintains it, and they're often used together.

The one-line mental model

Almost every "which one?" question dissolves once you place the task on two axes: provisioning vs. configuration, and declarative vs. procedural. The two tools were built for opposite corners.

Provisioning · Declarative · Stateful

Terraform

"Here is the infrastructure that should exist — make reality match it."
Creates & destroys cloud resources: VMs, VPCs/subnets, load balancers, managed databases, DNS records, IAM, Kubernetes clusters, even SaaS objects (GitHub repos, Cloudflare, Datadog). You describe the end state; it diffs against a state file and computes the create/update/destroy plan.
Configuration · Procedural · Stateless

Ansible

"Here are the steps to bring these machines to a known state — run them, in order, idempotently."
Configures the inside of machines that already exist: installs packages, templates config files, deploys app code, restarts services, patches fleets, orchestrates rolling deploys, configures network gear. Connects over SSH/WinRM — no agent, no state file. Re-run anytime to re-converge.

"They both just define → apply → converge. So what's the real difference?"

Fair challenge — on the create path they genuinely look identical. The difference stays hidden until the second run, and it reduces to one property: does the tool keep a ledger of what it made? Terraform does. Ansible doesn't. Watch what happens when you remove a resource:

And the physical reason neither can fully cover for the other

  
Even setting the ledger aside, the two act on different planes. A cloud's management API can conjure a VM but can't apt install inside it; an SSH session can configure an OS but can't summon the box it isn't on yet. That gap is structural, not a missing feature.

  

    
  

  
Each tool can lean across the line — Terraform provisioners, Ansible's cloud modules — but the moment it does, it loses the very thing that made it good (state-tracked lifecycle for Terraform; simple stateless convergence for Ansible). That's why "just use the one I already have for everything" quietly stops working as the job grows.







  
"...so just use Terraform for everything"? Here's the mirror image

  
The delete test was a biased sample — it showed the one axis where Terraform's model wins. Its closed-world authority ("this config is the whole truth; destroy anything I didn't declare") is a superpower on the control plane. Point that exact same property at the inside of a running OS and it becomes a wrecking ball. A typical server carries ~10,000 packages, files, services, users, and cron jobs. You care about three.     The kernel of truth in your instinct, though: the industry really is consolidating toward Terraform's declarative side — immutable infrastructure and containers. But watch where the config work goes: it doesn't vanish, it relocates from run-time (Ansible converging a live server) to build-time (a Dockerfile or Packer template baking an image that Terraform then rolls out). And a Dockerfile is still an ordered list of imperative RUN steps — the procedural config problem didn't disappear, it just moved earlier. So "Terraform for everything" in practice means "stop having mutable servers to configure," not "Terraform configures servers." For brownfield boxes, on-prem, network gear, stateful databases, and ad-hoc day-2 ops ("SSH to these 50 hosts and rotate this cert now"), mutable config management is still very much alive — that's just not a job Terraform's state-reconciliation model was ever built to do.

          The pattern that ends most arguments: use both
          
  
          They're not really competitors — they own different phases of the same lifecycle. The canonical pipeline hands off from one to the other.
          
  
          
    
  
          
  
          Terraform stands up the network, VMs, and managed services → emits IPs/hostnames → Ansible connects in to install, configure, and deploy. (For immutable infra, swap Ansible's role onto Packer at bake time and let Terraform roll out the finished image.)
