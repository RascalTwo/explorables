Federated credentials vs client secrets — what's actually on the wire

A generic walkthrough of CI → identity provider → cloud storage, under OIDC federation and under a client secret. Both paths end at the same object with the same authorization check; they diverge only in the shaded band up top — how the job comes to hold something the token endpoint will accept. Every claim carries a provenance chip, because a page that says "byte by byte" has no business guessing at bytes.

Federated (OIDC / workload identity) KEYLESS

No secret exists anywhere. The CI provider signs a fresh, single-purpose assertion per run; the token endpoint verifies it against a public key it fetched earlier.

Client ID + secret BEARER

A long-lived password sits at rest in the CI secret store, gets injected into the job env, and is posted to the token endpoint. Possession is identity.

Who calls the token endpoint, and when?

Not azure/login, and not once per job. The backend is compiled into the terraform binary and resolves credentials in its own Configure() before any provider process launches — so terraform itself does the OIDC fetch and the token exchange. And because every terraform invocation is a separate OS process whose token cache is memory-only, each command re-authenticates from scratch. Three commands means three GitHub JWTs and three token exchanges. Colour = who's being talked to.

How long a stolen artifact stays useful

Log scale, spanning five orders of magnitude — that spread is the entire argument. Solid = the floor; hatched = the documented range or the uncertainty. The federated artifacts expire on their own; the secret expires when a human remembers.
