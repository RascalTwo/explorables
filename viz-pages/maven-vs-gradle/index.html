JVM build tools · state of play, August 2026

Maven vs Gradle

For most JVM projects this really is tabs-versus-spaces, and pretending otherwise wastes everyone’s time. There are exactly four constraints that turn it into a real decision — two forcing each way — and outside those it is taste. This page scores twelve dimensions, lets you re-weight them by what you are actually building, and shows you where the four hard edges are.

02 · root cause

Every row above has the same cause

Those twelve dimensions are not twelve independent findings. They are one architectural decision, read twelve ways. A POM is data you parse. A build script is a program you run. Every advantage and every complaint either tool has falls out of that, which is also why the argument never resolves — each side is naming a different face of the same coin.

03 · mechanism

Why the speed gap exists at all

It is not that Gradle’s compiler is faster — they both shell out to javac. The gap is structural. Maven runs a fixed linear lifecycle: phases in a fixed order, every phase every time, with no memory of the last run. Gradle builds a task graph and asks each node “have your inputs changed since last time?” before running it. Everything else — the 2×, the 40×, the marketing — falls out of that one difference.

What am I looking at: the same project built five ways. Each node is a phase (left) or a task (right); fill colour is what happened to it. The bar under each column is wall-clock, drawn to scale — longer bar, slower build, same scale on both sides. Steps 1–4 favour Gradle; step 5 is the one that goes the other way, and it is the loop you spend the most time in.

the honest footnote

Maven’s column is not fixed at that height forever. mvnd (the Maven Daemon, a GraalVM-native client over a warm JVM) removes the per-invocation start-up cost, and the maven-build-cache-extension adds real input-hashing and cache reuse. Both are opt-in add-ons rather than the default, which is exactly the point: Gradle ships this behaviour as the tool, Maven ships it as something you have to go and adopt.

whose benchmark is this

Every number above is from Gradle’s own comparison page — a vendor benchmarking itself against a competitor. Three things it says in its own footnotes: the runs are on a 2018 MacBook Pro; the biggest multipliers require Develocity’s remote build cache, which is a paid product; and the incremental numbers (the 7×–85× ones) assume Maven’s incremental compile is broken and therefore compare Gradle’s incremental build against a Maven clean build. That assumption is not unreasonable — it is a genuine, long-standing Maven complaint — but it is doing most of the work in the headline.

05 · pros and cons, unhedged

What each one is genuinely good and bad at

Apache Maven
▲ pros
  • Convention over configuration. One project layout, one lifecycle, one answer. You can open a Maven repo you have never seen and know where everything is.
  • The POM is data, not code. IDEs, CI, SBOM generators, Dependabot and Renovate can all read a pom.xml without executing it. That is a bigger deal than it sounds.
  • Near-total stability. POMs written in 2012 still build in 2026. Maven 3.9.16 still runs on Java 8, which matters if your estate does.
  • Twenty years of matching answers. The plugin corpus is the largest in the JVM world and your exact error message is already on Stack Overflow.
  • 67% share means every new hire already knows it. Onboarding cost is zero.
  • Hard to make weird. Escaping the conventions takes deliberate effort, so builds stay legible even on teams that do not care about builds.
▼ cons
  • No first-class incremental build or build cache. A no-op rebuild costs roughly what a cold one does. This is the complaint.
  • XML. Verbose, no expressions, six lines to name one dependency, and conditionals smuggled in through profiles.
  • Custom logic means writing a Mojo — a separate plugin artifact with its own groupId, version and release cycle. There is no “just put four lines here”.
  • A cold JVM per invocation, unless you go and adopt mvnd.
  • Java-centric. Kotlin, Scala, JS and native targets are second-class or simply absent.
  • Maven 4 has been in release candidate since 2024 and is still not GA as of rc-6 (Aug 2026). The good stuff is real but you cannot depend on it yet.
Gradle
▲ pros
  • Genuinely fast, by design. Per-task up-to-date checks, local and remote build cache, configuration cache, parallel execution, a warm daemon. Not one trick — five.
  • Concise. Roughly 35 lines against Maven’s 62 for the same project; the Kotlin DSL gives you type-safe autocomplete on the build itself.
  • Extensible in place. Four lines in the build script beats publishing a plugin artifact to do the same job.
  • Polyglot and multiplatform. Java, Kotlin, Groovy, Scala, Android, C/C++, Swift, JS — first-class, not bolted on.
  • The Wrapper pins the tool version in the repo. Everyone and CI run the identical Gradle with no install step. Maven copied this later, for good reason.
  • It is the only supported build tool for Android. The Android Gradle Plugin has no Maven equivalent. For that one use case the comparison ends here.
▼ cons
  • The build is a program, so it accrues bespoke logic the way programs do. Over five years build.gradle drifts in a way pom.xml does not.
  • The two-phase model — configuration, then execution — is a real conceptual hurdle, and most genuinely confusing Gradle bugs live inside it.
  • An upgrade tax on every major. Gradle 9 forced Java 17, jumped to Groovy 4 and Kotlin 2.2, removed jcenter() and deleted deprecated APIs; third-party plugins touching internal APIs broke.
  • IDE sync must execute your build logic to know what the project is. That is precisely why Isolated Projects had to be invented.
  • Two DSLs, Groovy and Kotlin, splitting the documentation, the examples and every answer you find.
  • The best numbers need a paid product. Develocity’s remote cache is where the biggest multipliers come from.

07 · where this is going

They are stealing from each other

The interesting thing about 2026 is that the two roadmaps point at one another. Maven 4 is adopting the daemon, the cache and the CI-friendly versioning that made Gradle fast. Gradle 9 is adopting the isolation and cacheable-by-default determinism that made Maven predictable.
