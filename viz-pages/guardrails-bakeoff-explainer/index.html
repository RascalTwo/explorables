Guardrails Packaging Bake-off

Same guardrail brain, five ways to ship it. We changed only the packaging and measured what each costs. TECHN=5 per case · judge held constant (gemma4:e4b via LiteLLM).

A "guardrail" sits between users and an AI model and enforces rules — block prompt-injection, mask personal data (SSN, cards, phone), refuse banned claims. The rules were identical in every test. The question was purely: which package of the guardrail software do we keep?

1The five options

The same recipe, packaged five ways. The key pair: OSS + Parity (raw OSS with the missing pieces added back, which reaches the Custom Image) and Microservice + Parity (the same idea on the microservice, which doesn't).

TECHWhat is each one, in actual code?

The four "options" are four different *kinds* of artifact. Two are Dockerfiles you build, one is "clone someone else's repo and build theirs," and one isn't a Dockerfile at all — you pull a finished image and run it with config.

2What's actually in the box

All five carry the same engine and the same custom rules. They differ in two parts — the personal-data detector and the tracing pipe — which is exactly what makes a guardrail useful. Green ✓ = present and working.

The Custom Image ships both parts. The Raw OSS Image ships neither in working form. The OSS + Parity build is the Raw OSS image with those two parts added back — so it matches the Custom Image. The Microservice ships tracing but not the detector by default — its paved-path PII is a GPU model, though a CPU library works too (that's what Microservice + Parity does).

One nuance on personal-data masking — it comes in three tiers, and none of them needs a GPU here.
① Roll-your-own — regex + a little Python. Cheap, brittle, no model.
② Presidio — a CPU library (spaCy NER). This is the tier every contender above uses — every ✓ and ✗ in the masking rows is about tier ②.
③ NVIDIA GPU NIM — a dedicated GPU classifier. The microservice's paved path; we never ran it (no GPU).
So "needs a GPU" only describes tier ③. The Raw OSS gap was a missing spaCy model (tier ②, one CPU line); the Microservice gap was a missing Presidio library (also tier ②, CPU) — both fixable without a GPU.

TECHWhy Raw OSS is dark (verified live): not "no OTel libs" — the image actually ships the OTLP exporter and OTEL_EXPORTER_OTLP_ENDPOINT is set. It's dark because it launches as bare nemoguardrails, not under opentelemetry-instrument, so nothing wires the exporter to the global TracerProvider; NeMo's adapter "opts into the global tracer," which stays a no-op → 0 spans reach Phoenix (fired live; 0 spans in 10+ min). The operative fix in the parity layer is the opentelemetry-instrument entrypoint (+ openinference-instrumentation-langchain), not the exporter install.

6The verdict (advisory — a human decides)

We migrated: Custom Image → Microservice + Parity. We started on the Custom Image — a container we built and pinned ourselves. We moved to the microservice (with Presidio bolted on for PII) because it's the option with the least custom code we own: it's NVIDIA's productized box on the NIM-Operator path the team already runs in prod, and "parity" is just a thin CPU-Presidio layer following NVIDIA's own documented custom-deps build — not a full bespoke image we have to maintain forever.

It gives us everything we want. Full behavioral parity with the Custom Image: 5/5 cases, every rail type firing, the LLM-judged self-check working, and rich rail/action/judge traces that correlate end-to-end under the inbound trace (once OTEL_SDK_DISABLED=False is set — the wrapper defaults it to True and strips the adapter).

The one thing we don't want is network-gated to "not applicable." The microservice ships an unauthenticated config API (gate #4 — a live kill-switch that can delete the running rules). We don't remove it; we make it unreachable: loopback-only bind locally (the LAN refuses it, verified), and ClusterIP + gateway auth / NetworkPolicy in prod. Nothing that can reach the endpoint is untrusted, so the open API never matters. The Custom Image and OSS + Parity stay on the bench as functionally identical, all-gates-passing fallbacks.
