Act 1 · the app, and the pain

Meet Snapvault — then try to run it by hand

Two containers isn't interesting — you'd open two terminals and move on. The interesting case is a graph of services that have to come up together, find each other, and share state. So meet Snapvault, a small photo-backup SaaS: eight services, realistic, not insane.

Step 1: run it locally, by hand. Welcome to your eight terminals.

There's no orchestrator yet, so you are the orchestrator. Eight run invocations, in dependency order, each with the right --network, -e, -v, and --health flags — every single time you sit down to work:

…and that's the happy path. Forget --network backend on one and api can't resolve postgres. Start a worker before minio is healthy and it crash-loops. Tear-down is eight rms in reverse. Here's the whole dance as one script — scroll it and feel the ache:

run-snapvault-by-hand.sh (the full thing — what you do without an orchestrator)↕ scroll
#!/usr/bin/env bash
# What `docker compose up` does for you — done the hard way, by hand.
set -euo pipefail

# networks + volumes first (compose makes these implicitly)
docker network create frontend
docker network create backend
docker volume create pgdata
docker volume create redisdata
docker volume create blobs

# ---- data tier: must be up AND healthy before anything depends on it ----
docker run -d --name postgres --network backend \
  -e POSTGRES_USER=snap -e POSTGRES_PASSWORD="$POSTGRES_PASSWORD" \
  -e POSTGRES_DB=snapvault -v pgdata:/var/lib/postgresql/data \
  --health-cmd 'pg_isready -U snap -d snapvault' --health-interval 10s \
  postgres:16

docker run -d --name redis --network backend \
  -v redisdata:/data redis:7 redis-server --save 60 1 --maxmemory 256mb

docker run -d --name minio --network backend \
  -e MINIO_ROOT_USER="$MINIO_ROOT_USER" -e MINIO_ROOT_PASSWORD="$MINIO_ROOT_PASSWORD" \
  -v blobs:/data quay.io/minio/minio server /data --console-address :9001

# ...now WAIT for health, by hand, by polling. compose did this with one line.
echo "waiting for postgres..."
until [ "$(docker inspect -f '{{.State.Health.Status}}' postgres)" = healthy ]; do sleep 1; done

# ---- app tier ----
docker run -d --name api --network backend \
  -e DATABASE_URL="postgres://snap:$POSTGRES_PASSWORD@postgres:5432/snapvault" \
  -e REDIS_URL=redis://redis:6379/0 -e S3_ENDPOINT=http://minio:9000 \
  -e S3_BUCKET=photos -e JWT_SECRET="$JWT_SECRET" \
  ghcr.io/acme/snapvault-api:1.4
docker network connect frontend api   # api lives on BOTH networks

# three workers — by hand, one at a time, because "replicas: 3" isn't a thing here
for i in 1 2 3; do
  docker run -d --name "worker$i" --network backend \
    -e REDIS_URL=redis://redis:6379/0 -e S3_ENDPOINT=http://minio:9000 \
    ghcr.io/acme/snapvault-worker:1.4 celery -A snapvault.worker worker
done

docker run -d --name scheduler --network backend \
  -e REDIS_URL=redis://redis:6379/0 \
  ghcr.io/acme/snapvault-worker:1.4 celery -A snapvault.worker beat

docker run -d --name web --network frontend \
  -e NEXT_PUBLIC_API_URL=https://snapvault.local/api \
  ghcr.io/acme/snapvault-web:1.4

docker run -d --name nginx --network frontend -p 443:443 -p 80:80 \
  -v ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro \
  -v ./nginx/certs:/etc/nginx/certs:ro nginx:1.27
docker network connect backend nginx

# Teardown? Reverse ALL of it, every time:
#   docker rm -f nginx web scheduler worker3 worker2 worker1 api minio redis postgres
#   docker network rm frontend backend  # (volumes too, if you want a clean slate)

😮‍💨 Doesn't that suck?

That's a pile of fragile, ordered, copy-pasted ceremony to start one app on one laptop — and you re-run it every morning. This — not "I have two containers" — is the hole that needs filling.

Enter Docker Compose

Docker Compose is a tool for defining and running multi-container applications. You describe the entire stack — every service with its image and env, the networks, the volumes, and the dependency edges between them — in one declarative YAML file. Then a single command, docker compose up, reads that graph and creates and starts the whole thing at once (docker compose down tears it all back out).

Here's the full file for Snapvault — the same eight services from the diagram, the entire thing, scroll through it:

docker-compose.yml (the whole file)8 services · 2 networks · 3 volumes · ↕ scroll

What Compose buys you here

Look back at the by-hand script, then at the file: everything the eight-terminal slog did manually is now declared once. The dependency edges (depends_on … service_healthy), name-based discovery (postgres:5432 instead of an IP), shared named volumes, scaling (replicas: 3), and a single up/down for the whole graph.

🎯 The bar to clear

Hold this list — anything that wants to replace Compose has to handle all of it: the dependency edges, name-based service discovery, shared volumes, scaling a service, and one-command up/down. We'll grade every option against it.

Act 2 · why leave a good thing

You love Compose. So why would anyone walk away from Docker?

Compose just saved your afternoon — fair to ask why you'd change anything. The catch is that the reasons teams leave usually aren't about Compose the file. They're about Docker the platform underneath it.

💸 Licensing — the big one

Docker Desktop needs a paid subscription for organizations with more than 250 employees OR more than $10M/yr revenue (in force since 2022). The Compose file format and Docker Engine are open source — but Desktop is what most devs actually install, so it's what triggers a procurement conversation. For a lot of shops, this is THE reason, full stop.

🛡️ One big root daemon

Docker centers on dockerd — a long-running, usually-root background daemon; your containers are its children. One process to own, one root attack surface, one thing whose crash takes the whole host's containers with it.

🔓 Rootless by default

Security-locked clients (banks, gov, healthcare) want containers running as an unprivileged user with no daemon at all. That posture is exactly where Podman starts.

☸️ Kubernetes-shaped

If you're heading toward Kubernetes anyway, a tool that speaks pods and Kube YAML natively (the rest of this guide) beats one that only speaks its own format.

🐧 Enter Podman

Podman is a drop-in container engine that's fully open source (Apache-2.0), daemonless (containers are plain child processes — no background root service), and rootless-first. The CLI mirrors Docker's so closely that alias docker=podman carries most of your muscle memory over. No licensing question, no daemon.

First, the good news: almost everything carries over

Here's the reassurance that makes a switch survivable: your images, your Dockerfiles, and your registries don't change at all. Containers and images aren't a Docker invention or a Podman invention — they're a shared open standard, the OCI (Open Container Initiative), started in 2015 under the Linux Foundation (Docker donated the original runtime, runc, and the image format). A "Docker image" is an OCI image; Podman builds, pulls, and runs the very same artifacts from the very same registries. An OCI-compliant image runs on any OCI-compliant runtime.

Build once, run with either; push to any registry, pull with either. The container/image foundation is identical and portable — only the orchestration layer on top is tool-specific.

🧩 …so what actually differs? Just composition.

The single place the tools diverge is the layer for defining and running multi-container apps. Docker coined Compose; Podman offers a thin wrapper over it plus its own native answer (pods, borrowed from Kubernetes). That one layer is the entire subject of this guide — everything beneath it just carries over untouched. So, naturally, the first move is to look for compose on Podman…

"It's Podman now. So… podman compose, right?"

Reasonable instinct. Podman ships a compose subcommand, and a separate podman-compose tool exists too. Point either at your existing docker-compose.yml and a lot of the time… it just comes up. Let's be fair and bank the real wins first:

Why reaching for a compose tool is genuinely smart

  • Your YAML survivesThe same docker-compose.yml from Act 1 — no rewrite to learn a new format on day one.
  • The whole mental model transfersup, down, logs, ps, services, depends_on, named volumes — every concept you know maps over.
  • Rootless & daemonless underneathYou inherit Podman's actual selling points: no root daemon, containers as plain child processes.
  • Fastest possible migrationThe lowest-effort way to get a Compose stack onto Podman today.

✅ Honest verdict so far

For dev loops and simple stacks, a compose tool on Podman is a legitimately good answer. If that's all you need, you might stop here and be happy. The trouble only starts when you ask what is actually running when I type that command — which is Act 3.

Act 3 · read the label

The catch: "podman compose" is two different things, and neither is native

If something feels off, that's the right read. There is no single first-party Podman Compose engine. There are two separate tools wearing similar names, and the headline one is — in Podman's own words — a thin wrapper.

podman compose (the command) is just a wrapper — it delegates to one of two external providers depending on what's installed. Neither is a native Podman compose engine.

First, get the names straight, because they look identical and aren't. podman compose (with a space) is the command you type, and it implements nothing — it hands your file to a provider. There are exactly two, and the command picks whichever is installed:

Path A · provider docker-compose the default

If docker-compose is on the box, the wrapper hands your file straight to it — docker-compose "takes precedence." It's the real Compose engine, so you get full fidelity; it drives Podman through Podman's Docker-compatible API socket. So in the common case, podman compose literally "calls docker-compose under the hood." The catch: you're now running Podman in a Docker costume — a daemon socket, the very thing Podman was meant to get away from.

📎 podman-compose man page

"podman compose is a thin wrapper around an external compose provider… The default compose providers are docker-compose and podman-compose. If installed, docker-compose takes precedence."

Path B · provider podman-compose the python one

No docker-compose installed? The wrapper falls back to podman-compose — a separate community Python tool. Mind the hyphen: podman-compose (the package) ≠ podman compose (the command). It does not call docker-compose. It parses your file and emits podman CLI commands directly — no socket, no Docker binary, genuinely daemonless. Cleaner in spirit, but Red Hat's caveat stands:

⚠️ The honest limitation

"Podman Compose is not perfect because it implements a subset of the functionality of Docker Compose."

So that's the whole picture: one path calls docker-compose (full fidelity, but a Docker socket in disguise), the other is a Python tool that runs podman commands (daemonless, but only a subset of Compose). Either way, the podman compose command itself orchestrates nothing — it's a launcher for someone else's engine. (You can also invoke either provider directly — docker-compose against the podman socket, or podman-compose straight — the wrapper is just convenience.)

What the compose route gets right

  • Reuses your file & muscle memoryCovered in Act 2 — real and valuable.
  • Path B is genuinely daemonlessThe Python tool → straight to podman CLI, no socket.
  • Path A gives full fidelityBy delegating to the real engine, you get real Compose behavior.

Why it's a detour, not the destination

  • Not native / not first-partyThe subcommand is a launcher; the engine is something else (docker-compose or a community port).
  • Behavior depends on what's installedSame command, different engine, different results across machines. Fragile to reason about.
  • Subset gaps (Path B)A Compose feature subset — corners of your YAML may silently misbehave.
  • Docker-costume (Compose v2 path)Re-introduces a daemon socket — undoing a key reason you moved to Podman.

🧭 So what is the native answer?

Podman's own maintainers don't point at any of these for the long term. They point at the thing Podman borrowed straight from Kubernetes — the unit your containers were always secretly grouped into. Pods. →

Act 4 · the native primitive

Pods: the Kubernetes idea baked into Podman (it's in the name)

You heard right — Podman's native grouping is the pod, lifted from Kubernetes. A pod is "a container of containers": a set of containers that share a namespace, a network, and a lifecycle, started and stopped as one unit. This is the part Podman does itself, no wrapper, no second tool.

The one diagram that explains pods: shared loopback vs. bridge DNS

The deepest difference from Compose is how containers find each other, and it's worth seeing side by side.

Compose: each service is its own network endpoint, found by DNS name over a bridge. Pod: every container shares one network namespace via a hidden infra container, so they reach each other on 127.0.0.1 — like processes on one host.

🧭 The distinction in one line

In Compose, each service has its own IP (and any service can sit on, say, :8080 because it owns its address). In a pod, it's one shared IP and one shared port space — containers are split apart by port, not by address, just like processes on a single host. That's the whole essence of it.

🔌 The infra container (the "pause" container)

Every pod quietly runs one tiny extra container — the infra container. It holds the shared network namespace open so the real containers can join it and come/go without tearing networking down — the boilerplate glue. That's why they all see the same 127.0.0.1 and the same port space.

So inside a pod, your API reaches Postgres at 127.0.0.1:5432, not postgres:5432. That's a real config change from your Compose file — and it leads straight to the one gotcha worth flagging:

⚠️ One port space → port collisions inside the pod

Because every container in a pod shares the same network namespace, they share one set of ports. Two containers that both default to :8080 can't coexist in the same pod — the second fails to bind. Usually a non-event (most of Snapvault's ports differ), but if you happen to pack two :8080 services together, it'll yell at you. Re-map a port or split them into separate pods.

How you actually drive pods: Kubernetes YAML, not docker-compose.yml

Raw podman pod create + N × podman run --pod works but is just the manual pain again. The native, declarative way is to speak Kubernetes:

the native pod workflowno compose engine involved
# Already have it running by hand? Export it to a Kube YAML:
$ podman kube generate snapvault-data -f snapvault.yaml

# Bring the whole thing up from that YAML — Podman orchestrates it itself:
$ podman kube play snapvault.yaml

# Tear it all down:
$ podman kube play --down snapvault.yaml

(kube play / kube generate are the current names; you'll also see the older play kube / generate kube spelling in tutorials — same commands.)

The actual Kube YAML — put it next to the compose file

This is the artifact you'd generate or hand-write. As you scroll, watch the lesson the diagram set up: the data tier is one pod whose containers talk over 127.0.0.1 — but the API (a separate Deployment) reaches that pod by Service name again. Cross-pod, you're back to DNS, not localhost.

# Data tier = ONE pod (containers share 127.0.0.1). App tier = Deployments
# that reach the data tier by Service NAME (cross-pod = DNS, not localhost).

# ===== persistent volumes =====

kind: PersistentVolumeClaim
metadata: { name: pgdata }
spec:
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 10Gi } }

apiVersion: v1

  resources: { requests: { storage: 1Gi } }
---

kind: PersistentVolumeClaim
metadata: { name: blobs }

# ===== data tier: ONE pod, everything inside talks over 127.0.0.1 =====

kind: Pod
metadata:
  name: snapvault-data
  labels: { app: snapvault, tier: data }

      env:
        - { name: POSTGRES_USER, value: snap }

      volumeMounts:
        - { name: pgdata, mountPath: /var/lib/postgresql/data }
    - name: redis
      image: docker.io/library/redis:7
      ports: [ { containerPort: 6379 } ]
      args: ["redis-server", "--save", "60", "1", "--maxmemory", "256mb"]
      volumeMounts:
        - { name: redisdata, mountPath: /data }
    - name: minio

      env:
        - { name: MINIO_ROOT_USER, value: admin }
        - { name: MINIO_ROOT_PASSWORD, value: changeme123 }
      volumeMounts:
        - { name: blobs, mountPath: /data }
  volumes:
    - { name: pgdata,    persistentVolumeClaim: { claimName: pgdata } }
    - { name: redisdata, persistentVolumeClaim: { claimName: redisdata } }
    - { name: blobs,     persistentVolumeClaim: { claimName: blobs } }
---
# A Service so the app tier can find the data tier by NAME (cross-pod = DNS).
apiVersion: v1
kind: Service
metadata: { name: snapvault-data }
spec:
  selector: { app: snapvault, tier: data }
  ports:
    - { name: pg,    port: 5432 }
    - { name: redis, port: 6379 }
    - { name: s3,    port: 9000 }
---

apiVersion: apps/v1

  • Kubernetes-shapedThe YAML is real K8s — the same file graduates to a cluster.
  • One-unit lifecycleStart/stop/inspect the whole pod at once; tight, low-latency localhost between containers.
  • Daemonless & rootlessFull Podman benefits intact.

Pods — the sharp edges

  • Shared port spacePort collisions inside a pod; you re-plan ports vs. Compose.
  • Discovery by localhost, not namepostgres:5432 → 127.0.0.1:5432 within a pod (and back to Service names across pods).
  • No depends_on / no buildKube YAML has no Compose-style ordering or image-build step — you build images separately and handle startup readiness yourself.
  • New file format to learnKube YAML ≠ Compose YAML. Real, transferable, but a learning tax.

🤔 Honest gap

One giant pod is rarely the right shape for eight services — you don't want all of them sharing one port space and one failure domain. As in Kubernetes, you'd use several pods (data in one, app tier in others). Which raises the obvious question: who keeps all those pods running, restarts them, brings them up at boot? That's the last step.

Act 5 · the destination

Welcome to Podman world: kube play + Quadlet

The piece that makes pods a real Compose replacement on a single box isn't another compose clone — it's letting systemd be the orchestrator. Podman's Quadlet (since Podman 4.4) lets you describe containers, pods, networks and volumes as little declarative unit files, and systemd runs them: starts them at boot, restarts on failure, manages dependencies.

So how do you actually deploy this — keep the pod alive, restart it, bring it up at boot? Quadlet gives you two shapes, and they're not a coin flip: which you pick is a bet on where this app is headed.

🔱 The fork is about destination, not taste

The .kube file → stay in the Kubernetes lane. The YAML is portable to a real cluster; systemd just supervises it. Pick it if this box might not be the final home, or you already think in pods / Deployments / Services.

Native units → declare this node IS the destination and let systemd be the orchestrator a cluster would otherwise be. You drop Kubernetes YAML entirely. Pick it if there's no cluster in your future and you want per-service systemd control.

Way 1 — the .kube file portable

Stay Kubernetes-aligned. One small unit that points systemd at the snapvault.yaml from Act 4 and lets kube play bring the whole pod up. You keep thinking in Kubernetes objects, so the same YAML still graduates to a real cluster later.

snapvault.kube~/.config/containers/systemd/
# A Quadlet file. It LOOKS like a systemd unit, with Podman-only sections.
[Unit]
Description=Snapvault stack
After=network-online.target

[Kube]
Yaml=snapvault.yaml          # ← your pod(s) from Act 4

[Service]
Restart=always               # systemd keeps it alive

[Install]
WantedBy=default.target

🤔 Wait — is a .kube file a systemd unit?

Almost — this trips everyone up. Quadlet is a systemd generator. You author this friendly file; on systemctl daemon-reload, Podman's Quadlet generator compiles it into a real .service unit and systemd runs that — you never hand-write the gnarly ExecStart=podman … line. (Same trick for the .container / .pod / .volume files on the right.)

Whole footprint: two files — this plus the snapvault.yaml from Act 4. Then systemctl --user start snapvault.service and the stack is up. If you already wrote the YAML, you're adding exactly one file.

Way 2 — native units this-node-is-it

The off-ramp to plain systemd. No Kube YAML at all: each container, the pod, and each volume is its own little unit. In exchange you get per-service control — independent restarts (systemctl restart api bounces only the API), After=/Requires= ordering (the depends_on raw pods lacked), per-unit limits, and per-service logs. For Snapvault that's one .pod + three .volumes + eight .containers = 12 files:

the complete native Quadlet set (12 files)↕ scroll

#   systemctl --user daemon-reload && systemctl --user start snapvault-pod.service
# One pod, so every container talks over 127.0.0.1 (the Act 4 lesson).

PublishPort=443:443

[Install]

[Install]

[Unit]
Description=Snapvault — nginx (front door)
After=web.service api.service
[Container]
Image=docker.io/library/nginx:1.27
Pod=snapvault.pod
Volume=%h/snapvault/nginx.conf:/etc/nginx/nginx.conf:ro,Z
[Install]
WantedBy=default.target

Notice the networks vanished: one pod = one shared netns, so the pod is the network and containers wire to each other on 127.0.0.1. (Want the isolation back? Split into several pods.) And After=/Requires= on api.container is the dependency ordering raw kube play couldn't express.

🚪 So — is this just an "escape hatch"?

Half-right. It's not a fringe hack — native .container units are the idiomatic Quadlet way (Red Hat's replacement for the deprecated podman generate systemd). But the direction is right: here they're the off-ramp that keeps your whole stack running without ever committing to Kubernetes YAML, systemd playing the orchestrator a cluster otherwise would. Not a last resort — the deliberate "I'm not going to Kubernetes" fork. If a cluster is coming, take Way 1.

💻 …and this is for local dev too, not just servers

Drop these in ~/.config/containers/systemd/ and they run rootless, as your user (systemctl --user) — no root, no cluster, no production anything. That's the developer payoff: Compose's "one command and my whole stack is up and stays up," but native to Podman. (On a server you'd enable it at boot; on your laptop you just start it when you sit down.)
