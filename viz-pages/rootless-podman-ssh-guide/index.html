▣ Rootless Podman over SSH — setup guide

Run containers on a shared Linux box from your own machine — isolated, passwordless, no local Docker daemon.
← set these to yours; every command updates live

A shared Linux server becomes your rootless Podman backend: containers run there, you drive them from here. Four tasks below — the first, Passwordless SSH, is mandatory (nothing works until it's done); the rest build on it.

What you're setting up

You're turning a shared Linux server into a remote rootless Podman backend. You run podman and podman compose from your own machine, but the containers actually build and run on the server — no Docker Desktop, no local daemon, none of the heavy lifting on your laptop.

Rootless means Podman runs as you on that box: your containers, images, and data are yours alone. Many people share the same hardware yet stay fully isolated — the only thing you share is a range of host ports.

The four tabs below get you there: a passwordless SSH key (the foundation), an optional GitHub key, the Podman connection itself, then a multi-container Compose demo.

Behind the scenes

          
A keypair is two matched files, created together by that one command:

          
• ~/.ssh/podman — the PRIVATE key. Lives only on your machine. Anyone holding it can log in as you, so it never leaves.

             • ~/.ssh/podman.pub — the PUBLIC key (that's what .pub stands for). Harmless to share; this is the one you install on servers.

          
They're mathematically linked: a challenge signed by the private key can only be verified by its matching public key. That one-way link is how a server confirms it's really you without you ever sending a secret — only signatures cross the wire, never the private key.

          
A blank passphrase means the private key file isn't itself encrypted, so nothing has to be typed at connect time — which is exactly what lets Podman and automation run unattended.

🔐 What actually happens when you run ssh {{MACHINE}}

      
Public-key auth in five moves — no secret ever crosses the wire, only signatures.

      

      
    
        
  1. You run ssh {{MACHINE}}.
    2. 
        
  2. ssh opens ~/.ssh/config, finds the Host {{MACHINE}} block, and loads the key it names — your private ~/.ssh/podman.
    3. 
        
  3. ssh contacts the server, offers the matching public key, and signs the server's random challenge with your private key.
    4. 
        
  4. The server looks in ~/.ssh/authorized_keys (where ssh-copy-id put your public key in step 2) and uses that public key to check the signature.
    5. 
        
  5. Only your private key could have produced that signature, so the server is convinced it's you — and lets you in. No password.
    6. 
      


      
↩ The fallback — why an un-configured host asks for a password
        
SSH to a host that's not in your config (no IdentityFile set)? Then ssh has no specific key to use, so it falls back to its default-named keys — ~/.ssh/id_ed25519, ~/.ssh/id_rsa — plus anything in your agent.

        
The server doesn't have any of those public keys in its authorized_keys, so it can't verify you by key at all. Key auth doesn't error loudly — ssh just quietly drops to the next method and the server asks for your password. That's exactly the password prompt you got before setting up the config + key.

Shared hardware, isolated software

          
Several people can point their own Podman connections at the same box and never see each other. Your containers, images, and data all live under your home dir (~/.local/share/containers) on the server. Run podman image ls and you see yours; your coworker sees theirs.

🔐 How it all works — Podman driving the box over SSH

      
Every podman command you ran reached across the same SSH key from Passwordless SSH. Here's the whole path of a podman run … -p 8123:8080.

      
      
    
        
  1. podman run … on your laptop hands the request to Podman's built-in SSH client.
    2. 
        
  2. It connects to the server with your ~/.ssh/podman key — the exact handshake from Passwordless SSH — and reaches your rootless socket at /run/user/<uid>/podman/podman.sock.
    3. 
        
  3. Podman there pulls the image into your isolated store and starts the container as you — rootless, no root anywhere.
    4. 
        
  4. -p 8123:8080 publishes the container's port 8080 out to the server's port 8123.
    5. 
        
  5. Your browser hits {{MACHINE}}:8123 — the server, not localhost — and the server forwards it into the container.
    6. 
      

    


    

      Passwordless SSH + Podman backend done = you're running rootless containers on shared Linux, fully isolated, no password, no local Docker. 🎉
    

  


  
  

    
4 · Deploy a stack with Compose

    
Define your services in one file, bring them up with one command. Pick a flavor below.


    
ℹ Why this just works — the Podman backend step made {{MACHINE}} your default Podman connection, so podman compose automatically targets the remote. But it also leans on the Passwordless SSH ~/.ssh/config — full story in the explainer at the bottom.


    

      
      
    


    

    
Two containers that show compose's superpower — a database + a web UI that find each other by name, working in your browser in under a minute. Lightweight (~280 MB), all official images.


    

      
Create the compose file
Two services: a Postgres database + Adminer, a web UI for it.

      

        
In a new folder on your machine, save this as compose.yaml:

        
services:
  db:
    image: docker.io/library/postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: demopass
  adminer:
    image: docker.io/library/adminer:4
    environment:
      ADMINER_DEFAULT_SERVER: db
    ports:
      - "8200:8080"

        
Fully-qualified image names (docker.io/library/…) keep Podman from asking which registry to use. 8200 is the host port — pick any free one in 8000–9000. Note db publishes no port: only Adminer is reachable from outside; it talks to the database privately.

        
Behind the scenes

          
The file lives on your machine, but the containers run on {{MACHINE}}. podman compose reads the YAML locally and runs everything on your default connection's remote — same split as every other command in the Podman backend step.

Behind the scenes — where each value comes from

          
Compose created a private network and registered each service under its name. Inside that network, db resolves to the Postgres container's address — no IPs, no linking, no published port. You only exposed adminer to the outside; the database stays internal.

          
The Postgres image, given only POSTGRES_PASSWORD, creates a superuser named postgres and a database named postgres by default — that's why both Username and Database are postgres. 🔐 Why compose is special — and why Passwordless SSH's config mattered

      
podman compose doesn't speak compose itself. It hands off to an external engine that makes its own SSH connection — ignoring the identity you set on the Podman connection. Here's the split.

      
      
    
        
  1. podman run uses Podman's built-in SSH and the key you set with --identity (the Podman backend step).
    2. 
        
  2. podman compose hands off to an external engine that opens its own SSH connection and never sees that identity — it only reads ~/.ssh/config and default keys.
    3. 
        
  3. Same server, two different SSH clients, two config sources. That's why the key is named in both places — the connection (Podman backend) and ~/.ssh/config (Passwordless SSH). Two places, one key, by design.
    4. 
      


      
🛠 Troubleshooting — if podman compose up asks for a password
        
The engine's ssh isn't using your key. Re-check the Passwordless SSH step: ~/.ssh/config must have the IdentityFile line pointing at ~/.ssh/podman. The engine makes its own SSH connection and only reads that config — fix it there and compose connects. This is the exact payoff of that step.
