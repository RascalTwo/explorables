Terraform vs Ansible vs PowerShell DSC

Three ways to manage config-as-code, compared as tools — not as three ports of one provider. The short version: Terraform builds the house (declaratively, with a deed), Ansible furnishes & maintains it (procedurally, step by step), and DSC keeps each room exactly as-specified (declaratively, checking itself). DSC is the declarative middle child living on Ansible's turf.

The one-line mental model

Almost every "which one?" argument dissolves once you place the task on two axes: provision infra vs. configure the inside of a machine, and declarative end-state vs. procedural steps. Terraform and Ansible were built for opposite corners — and DSC claims the corner neither one covers.

Provision · Declarative · Stateful

Terraform

"Here is the infrastructure that should exist — make reality match it."
Creates & destroys cloud/SaaS resources: VMs, networks, load balancers, managed DBs, DNS, IAM, k8s, GitHub/Cloudflare/PingOne objects. Diffs your end-state against a state file and computes the create/update/destroy plan.
Configure · Declarative · Self-testing

PowerShell DSC

"Here is the state each resource should be in — check it, and fix only what's off."
Brings a node/resource to a declared end-state: files, registry, services, packages, roles — or, here, Keycloak/PingOne objects. Every resource implements Get / Test / Set, so idempotency and drift-checking are intrinsic. No central ledger.
Configure · Procedural · Stateless

Ansible

"Here are the steps to bring these machines to a known state — run them in order, idempotently."
Configures the inside of existing machines and orchestrates: installs packages, templates config, deploys apps, rolling restarts, patches fleets, "SSH to these 50 hosts and do X now." Connects over SSH/WinRM — no state file.
Read left→right, the three trace a path: Terraform makes the box → DSC/Ansible configure inside it. DSC and Ansible share the same territory; they disagree only on how you describe the work.

What you actually write

Those axes are real code. Here's the same job in each tool — "make sure the acme Keycloak realm exists, enabled, with a 5-minute access-token lifespan." All three declare the same desired end-state; only the syntax and the runtime differ. These are real snippets — the DSC ones are trimmed straight from the bake-off's own KeycloakDSC module.

Terraform main.tf · HCL
# provider "keycloak" { ... } set up elsewhere
resource "keycloak_realm" "acme" {
  realm                 = "acme"
  enabled               = true
  display_name          = "Acme Corp"
  access_token_lifespan = "5m"   # duration string
}
terraform apply → diffs vs the state file, then creates / updates.
PowerShell DSC apply.ps1 · v3
# connection + the realm's desired state
$conn = @{
  KcUrl            = 'http://localhost:8089'
  AuthClientId     = 'admin-cli'
  AuthClientSecret = $env:KC_SECRET
}
Invoke-DscResource -Name KeycloakRealm `
  -ModuleName KeycloakDSC -Method Set `
  -Property ($conn + @{
    Realm               = 'acme'
    Enabled             = $true
    DisplayName         = 'Acme Corp'
    AccessTokenLifespan = 300   # seconds
    Ensure              = 'Present'
  })
-Method Test instead → returns $true if already compliant (drift check, no state file).
Ansible realm.yml · YAML
# a task in a playbook
- name: Ensure the acme realm exists
  community.general.keycloak_realm:
    auth_keycloak_url: http://localhost:8089
    auth_realm: master
    auth_client_id: admin-cli
    auth_client_secret: "{{ kc_secret }}"
    realm: acme
    enabled: true
    display_name: Acme Corp
    access_token_lifespan: 300   # seconds
    state: present
ansible-playbook realm.yml → the module GETs, then POSTs/PUTs to converge, every run.
Same 5-minute lifespan, three type systems: Terraform takes a duration string ("5m"); DSC and Ansible take integer seconds (300).
One level deeper — the part DSC makes you write
In Terraform that declaration rides on a provider (Go, maintained upstream by HashiCorp/the community); in Ansible, a module (Python, upstream). No Keycloak DSC module existed — so the bake-off builds the resource layer itself: one [DscResource] class per resource. This is where idempotency and drift actually live — inside Test() and Set(), not in a state file. (Trimmed from the real module.)
[DscResource()]
class KeycloakRealm : KeycloakConnectionBase {
  [DscProperty(Key)] [string]         $Realm
  [DscProperty()]    [nullable[bool]] $Enabled
  [DscProperty()]    [string]         $DisplayName
  [DscProperty()]    [nullable[int]]  $AccessTokenLifespan
  [DscProperty()]    [Ensure]         $Ensure = [Ensure]::Present

  [bool] Test() {                       # ← drift check — no state file
    $rep = $this.Fetch()                # GET /admin/realms/{realm}
    if ($this.Ensure -eq 'Absent') { return ($null -eq $rep) }
    if ($null -eq $rep)            { return $false }
    return $this.FieldsMatch($rep)      # desired == actual ?
  }

  [void] Set() {                        # ← converge only what Test() flagged
    $rep  = $this.Fetch()
    $body = $this.DesiredBody()
    if ($null -eq $rep) { $this.Api('Post', $this.CollectionPath(), $body) }   # create
    else                { $this.Api('Put',  $this.SelfPath($rep),  $merged) }  # update
  }

  [KeycloakRealm] Get() { ... read current state → return an instance ... }
}
That Test()/Set() split is the whole "declarative + drift-aware, but stateless" story from the next sections, in code: Test() answers "is it already right?" against the live API, and Set() only touches what isn't — no ledger consulted, none written.

Where the three sit — the two-axis plane

The two axes carve four quadrants. Terraform, Ansible, and DSC land in three of them; the fourth (provision + procedural) is just hand-rolled scripts. The dashed triangle shows the punchline: each pair shares exactly one trait — which is why no two are interchangeable.

Ansible aims for declarative idempotency but is procedural underneath — order matters, and a raw shell: task is only as idempotent as you make it. DSC sits high because Get/Test/Set is enforced by the resource contract, not left to the author.

Why DSC is the "middle child," not a third rival

DSC isn't a fourth flavour of the same idea — it's a deliberate recombination. It takes Terraform's mindset (declare the end-state; the tool figures out the delta and can tell you what drifted) and applies it to Ansible's territory (the inside of a machine — stateless, additive, no central ledger to lock or corrupt). It's the only one of the three that is declarative AND on the config plane.

That recombination is exactly what makes DSC attractive for the bake-off's config-plane lane: it answers Ansible's biggest gap (no drift visibility) without taking on Terraform's biggest liability (a state file you must lock, protect, back up, and keep secrets out of).

The crux: state and drift-detection are separable

People assume "knows what drifted" requires "keeps a state ledger" — because Terraform bundles them. DSC pulls them apart: it keeps no central ledger, yet still answers "what's off?" on demand, because every resource self-tests (Test returns compliant / not). Two independent axes, three different answers:

Terraform buys drift-detection with a state file — powerful, but now you own a lockable, corruptible, secret-bearing ledger. Ansible gives up both: no ledger, no drift view — you re-run and hope it converges. DSC is the interesting combination: stateless like Ansible, drift-aware like Terraform. The cost it pays instead is a weak teardown (no ledger means no "reap everything I didn't declare") — the same trade Ansible makes.

Read the fine print: "DSC" means two very different things

If your mental model of DSC is "Windows-only, compile to MOF, background agent auto-applies" — that's classic DSC (v1–v2). DSC v3 (GA March 2025) is a near-total reframe, and it's the version the bake-off lane uses. Same resources, completely different runtime.

              They're not really rivals — they own different phases

              Terraform owns the provision phase; DSC and Ansible are two styles of the configure phase that follows. The canonical pipeline provisions first, then hands off — and the config step is where you choose declarative (DSC) or procedural (Ansible).

              Terraform stands up the infra and emits IPs/hostnames → then the config phase brings the inside to spec. Pick DSC when you want declarative desired-state with self-testing resources (Windows-heavy, continuous compliance); pick Ansible when you want ordered orchestration, multi-host workflows, or ad-hoc day-2 ops. For immutable infra, this whole config phase moves to Packer at bake time.
