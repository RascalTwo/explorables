Prioritizing requests on a busy GPU

Three ways LiteLLM can order requests under load — two built-in paths that fall short, and the ~35-line key-based gate we built. Measured on a live LiteLLM 1.85 + Ollama stack.
One on-prem GPU lane, only one request in service at a time. Two kinds of traffic share it: a live chat request that must be fast, and a nightly RAGFlow / batch job that can wait. When the lane is saturated, chat must be served ahead of batch — and a batch job must not be able to cheat the line. Press play: the same five requests drain through each policy.

priority bound to the key
LiteLLM's built-ins read priority from the caller (forgeable) or need rpm windows (flaky). Moving the decision onto the key — enforced at the gateway, ignoring whatever the body claims — is what makes it both un-cheatable and deterministic. It's the rare case where ~35 lines of our own code beats the platform feature, because the platform feature is structurally wrong for "priority the caller can't forge."
scenario: 1 blocker (batch, in service) + 2 batch + 1 chat + 1 cheat → one slot. drain order is computed per policy, exactly as observed on the stack.
