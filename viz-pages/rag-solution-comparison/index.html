Which RAG engine? Turnkey ↔ build, the honest map.

You already know what RAG is. Now the first real decision: which engine do you actually stand up? There's a spectrum — from turnkey appliances that "handle anything" out of the box to build-it-yourself frameworks you wire together — and no single right answer. This page is the honest map: the poles, a scored matrix, and the trade-offs, so you can pick the end that fits your team. A comparison that pretends one winner is unconditional is propaganda.

We built one engine at each end as worked examples — a turnkey appliance and an owned build — but neither is declared "the pick." The spectrum is the point: either end works.

the lens1Your preferences do most of the deciding

Before ranking anyone, decide what you actually want. Half the "best RAG platform" lists on the internet are answering a different question (cloud-hosted, single-app, one language). A common, defensible set of engineering preferences — the ones this map is drawn for — looks like this:

self-hostable · not vendor-locked

You prefer a solution you can run in your own infrastructure and aren't locked to a single vendor. Cloud-only engines (managed-store-only, hosted-only platforms) are out before you start. Models — LLM, embeddings, and reranker — are reached through an OpenAI-compatible API, so they work behind any gateway you already run.

The gate: a contender must let you point model calls at an arbitrary base URL. Most do. The awkward one is NVIDIA's RAG Blueprint — it's NIM-first: built to run NeMo Retriever NIMs you deploy yourself. It does expose OpenAI-compatible endpoints, but the happy path is running NIMs, not aiming the whole pipeline at an external gateway — a heavier, more opinionated footprint than "just point it at your gateway."

microservice · single responsibility

You favour a microservice architecture: single responsibility, do one thing well, composable services. The thing you build is a retrieval microservice — one app consumes it today; other teams may spin up their own instances and adapt it tomorrow. That second clause matters more than it looks.

The gate: "other teams run their own instance" is a multi-tenant-ish usage. That's exactly what Dify's license forbids without a written commercial grant (its enterprise build phones home to a license server). A genuine strike for a reuse-everywhere microservice — not a knock on Dify the product.

And the storage lever: consolidate on one database type where you can — fewer moving parts. Postgres is a safe, open-source default (with pgvector for embeddings). Hold that thought — §4 is about why a turnkey engine like RAGFlow often ships its own vector store instead of pgvector — and why that's fine.

Turnkey — "handle anything"

example: RAGFlow · Apache-2.0, no feature gates

You point it at messy real-world documents — scanned PDFs, multi-column layouts, tables — and it just ingests them. Hybrid search, reranking, GraphRAG and RAPTOR are all there, on by default.

you get
  • Best-in-class deep-document parsing (DeepDoc, optional VLM pipeline)
  • Native hybrid + RRF + rerank + GraphRAG/RAPTOR — no assembly
  • Headless, retrieval-only mode behind a clean API — call it over HTTP from any language
you give up
  • A heavy container footprint (its own vector store, doc engine, queue)
  • A fixed, opinionated pipeline — you tune the dials, you don't rewrite the machine
  • Its own vector store (Elasticsearch / Infinity) — not pgvector

Build — "tune it yourself"

example: Spring AI (Java) · Apache-2.0 — or LlamaIndex / LangChain.js

The pipeline is your code, in the app you already run — Java (Spring AI), Python (LlamaIndex), or TypeScript (LangChain.js). Retrieval advisors, a vector-store abstraction, ETL hooks — the scaffolding is there; the retrieval logic is yours to shape.

you get
  • Lightest footprint — it's a library, not another box to operate
  • pgvector first-class; OpenAI-compatible base-URL config is trivial
  • No ceiling on customization — tune retrieval to whatever the next team needs
you give up
  • Parsing fidelity — you bring/build the scanned-PDF + table story yourself
  • GraphRAG, RAPTOR, fusion, CRAG — hand-wired, not free
  • Time-to-first-answer — turnkey is running while you're still plumbing

the honest bit4About pgvector

"Vector database" often lands on pgvector first — and for good reason. It's one Postgres, no new server to operate, open-source, and the community has rallied hard around it. It's genuinely fine to tens of millions of vectors with solid hybrid (BM25 + vector) support. For a team getting started, or hand-building on the build pole, it's a strong, sensible default.

Honest caveat: pgvector is a sensible default, not the only viable choice. This isn't month one of the AI boom anymore — several purpose-built vector stores are mature and production-proven now: Qdrant, Milvus, and Weaviate are all reasonable picks if you'd rather run a dedicated store. pgvector wins on "one fewer thing to operate," not on being the only option.

And it's no longer just dedicated vector databases — vectors have gone mainstream in general-purpose engines. The industry trend is that your existing relational or document database probably already speaks vectors, so you may not need a new datastore at all: Microsoft SQL Server 2025 ships a native VECTOR type with VECTOR_DISTANCE (cosine / euclidean / dot) and DiskANN-based approximate nearest-neighbour search (VECTOR_SEARCH, still in preview); Oracle Database 23ai has a native VECTOR type + AI Vector Search; MySQL has vector storage + similarity search (GA, e.g. Cloud SQL for MySQL); and MongoDB exposes $vectorSearch. Postgres/pgvector is the open-source version of a much broader move — if you already run one of these, the "one fewer thing to operate" argument may already be won for you.

And a turnkey engine may not run on pgvector — that's not a broken promise. Plenty of turnkey engines do support pgvector, or let you choose among vector stores. But some bring their own, and RAGFlow specifically is one of them: it keeps vectors in Elasticsearch (or Infinity), rather than pgvector. (Others land elsewhere too — NVIDIA's Blueprint defaults to Milvus, Onyx to OpenSearch, migrating off Vespa.) When an appliance like RAGFlow bundles its own store, that store is part of what makes it turnkey — and that's fine. pgvector stays a sensible default for any team that builds its own; RAGFlow just brings a better-tuned trunk for the messy-document job.

When does a build-pole team outgrow pgvector? Past ~50–100M vectors, or when single-digit-ms p99 at that scale is the workload — then Qdrant (latency, hybrid) or Milvus (raw scale). Most reusable instances never get there.

the escape hatch5When the corpus won't sit still

RAGFlow's GraphRAG/RAPTOR layer is what makes it answer global, multi-hop questions — but those are a global recompute: many LLM calls, scaling with corpus size × how often it changes. On capable hardware that's fast, but it isn't free. For a living, churning corpus, that cost compounds.

the swap target

The incremental-native graph engines — LightRAG, fast-GraphRAG, LazyGraphRAG — fold new entities and relations into the existing graph without a full rebuild. Reported indexing cost runs 50–6000× below Microsoft-style GraphRAG on the same documents. They're not a turnkey app; they're the specialist library you drop in behind the same seam if RAGFlow's deep layer becomes the bottleneck.

The trigger is compute cost on a high-edit-rate corpus — not wall-clock, and not most corpora. Don't reach for this on day one. It's the documented Plan B, sitting one adapter away.

the call6No verdict — both ends work, you decide

There's no thumb on the scale here. Both ends are viable; we built one at each end as a worked example so you can see them for real. Here's the honest pros-and-cons of each — then it's your call.

Far-left: turnkey (e.g. RAGFlow)

it works — an appliance you configure, not code
pros
  • Best-in-class deep-doc parsing (scanned PDFs, tables, multi-column) out of the box
  • Hybrid + rerank + GraphRAG + RAPTOR native — no assembly, fast time-to-first-answer
  • Apache-2.0, no feature gates — teams can stand up their own instances freely
cons

  • Brings its own store (Elasticsearch / Infinity) — not pgvector
  • Fixed, opinionated pipeline — you tune the dials, you don't rewrite the machine

pros

Either way, don't shrink-wrap your RAG microservice.

The entire field above churns underneath you — parsers, rerankers, graph methods, vector stores are all moving fast. So whatever you pick today, don't bind your application code to it. Program to a stable interface, not a vendor: sit the engine behind a fixed contract — ports & adapters, hexagonal architecture — so swapping engines or upgrading a component later is writing an adapter, not rewriting your pipeline. That is what makes picking either end a reversible choice rather than a one-way door.

This project shows the move. The app never talks to the engine directly; it talks to a stable /api/v1 contract. The engine sits behind one seam — a reconciler on the write side, a retriever adapter on the read side. Flip RAGFLOW_BASE and the same clients keep working against the owned build instead — one env var, no caller touched. Swapping the backend is an adapter change, not a pipeline rewrite.

Watch the swap happen live: the engine toggle flips the turnkey ⇄ owned build in the running app, on that one variable, with the same clients unchanged. The generalization: whatever you choose off the spectrum, keep the seam — the ecosystem will move, and the adapter is how you move with it.
