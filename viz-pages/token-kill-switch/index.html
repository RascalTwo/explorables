Turning it off

A self-contained token cannot be recalled. Once it is signed and handed over, no message you send will reach the verifier that is about to accept it. So containment is not one action — it is a choice between five levers with wildly different speeds and wildly different collateral damage, and the choice has to be made before the incident, not during it.

Lever 4, in detail — because there are two of it

Every lever above except this one is a single action. Deny-listing is a design with two very different implementations, and which one you pick decides whether the issuer ends up on the path of every API call. They are frequently described as one thing. They are not.

Where the four steps come from

RFC 7519 §4.1.7 defines jti as a unique identifier whose value "MUST be assigned in a manner that ensures that there is a negligible probability that the same value will be accidentally assigned to a different data object", and says outright it "can be used to prevent the JWT from being replayed." Use of the claim is OPTIONAL — so if you want this lever, stamping it is step zero.

RFC 7662 defines introspection as "a method for a protected resource to query an OAuth 2.0 authorization server". A method — not a requirement. It names structured tokens as the alternative that does not need it. Nothing obliges you to introspect.

OWASP reaches the deny-list from the other direction: its JSON Web Token Cheat Sheet treats a jti deny-list, held until the token would have expired anyway, as the standard answer to invalidating a JWT before its own expiry.

Which one, and when

Neither, while the lifetime is short. Rows 1 and 2 of the chart above already contain the attacker within the token's own lifetime, at zero build cost and zero collateral. That is the default and it needs no new component.

Local deny-list, when that delay is too long. If the gap between deciding to stop someone and their traffic actually stopping has to be seconds rather than a token lifetime, this buys it. The check is an in-memory set lookup on the resource server, so the authorization server stays off the request path and can be down without taking the API with it. The cost is a propagation delay and one small control-plane channel.

Introspection, when even that is too slow. It removes propagation delay entirely and charges a network call to the issuer on every request, forever. The issuer becomes a hard dependency of every API call — the availability coupling that self-contained tokens exist to avoid.

The distinction worth keeping: revoking is rare and can tolerate a few seconds — that is a control-plane problem. Validating happens on every request and can tolerate nothing — that is the data plane. Introspection solves the rare problem by putting its mechanism into the common path. A local deny-list keeps them apart.

Elsewhere — the same lever, priced differently JSON Web Token Cheat Sheet· OWASP Cheat Sheet Series Its answer to "how do I turn one off" is lever 4 above — a deny-list keyed on jti, held only until the token would have expired anyway. Worth reading for the framing difference rather than a disagreement: it presents the deny-list as the standard solution to JWT revocation, and this page presents it as the one lever whose collateral never ends, because the issuer is now on the path of every API call. Both are true. Which one governs depends entirely on the token lifetime — the dial at the top of this page.
