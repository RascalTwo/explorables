Managing Microsoft as Code — pick your weapon

You want to stop clicking around the portal and manage your Microsoft cloud as code. Here are your real options — and the punchline: no single declarative tool reaches the whole surface (only imperative PowerShell does, by hand-rolling the idempotency the others give free), so you pick by what you're trying to touch, not by taste. (And one of them, Ansible, isn't even in the same race.)

The map

How far each tool reaches — across two different jobs

Two things get called "infrastructure as code," and they're different jobs. Day 1 — provision the cloud surface (the three left columns; harder to reach as you go right). Day 2 — configure what runs inside the machines (the far-right column). Bicep is a fortress on Azure. Terraform wades into identity. Only idempotent PowerShell reaches DLP/Purview. And Ansible owns a column the others can't touch at all — but it's a column that's empty if you run no VMs.

Reading it: the three Day-1 columns are one axis — the Microsoft cloud surface, getting harder to reach left→right, until only hand-written PowerShell gets there. The Day-2 column is a different axis entirely: configuring the guest OS + apps inside VMs. That's Ansible's home turf and the one bright-green cell no provisioning tool owns — and it goes dark for everyone (Ansible included) the moment you're all-PaaS / serverless.

The routing rule

"What am I trying to manage?" → the tool

Skip the religious war. The surface you're touching picks the tool for you.

The contenders

Pros, cons & the verdict

01–03 are the real fight over provisioning the Microsoft cloud, ranked by how much of the "as code" dream they deliver. ClickOps is on the board to be the loser. Ansible sits apart (≠) — it's not competing, it's playing a different game.

The provisioning mental model: declarative IaC (Bicep / Terraform) owns the ARM control plane — the resources. Everything else — identity in Entra, data-plane config in Purview / Exchange / Teams — is the escape hatch's job: idempotent PowerShell over Microsoft's admin modules, each just a glorified authenticated API call. Real shops run both side by side.
Where Ansible fits: it's not a rival to any of those — it owns Day 2, configuring the guest OS + apps inside your VMs (its real rivals are Puppet / Chef / PowerShell DSC). It can provision Azure via the Microsoft-maintained azure.azcollection, but that's redundant vs Terraform/Bicep. Its one uncontested value is the in-VM layer — essential if you run VM fleets, zero value if you're all Container Apps / Functions + M365.
Field note — capable ≠ approved. The winning tool isn't always the most capable one, it's the most capable approved one. In a real M365 Copilot rollout in a regulated environment, Terraform (the best declarative option) was org-banned — and since PowerShell already covers 100%, the shipped answer was PowerShell-only, hand-rolled idempotency and all. Two caveats ride along: the Bicep/Terraform gaps are maturity, not architecture — all three call the same Graph APIs, and the declarative ceiling is already rising (a preview msgraph Terraform provider can now do group licensing). The only truly un-automatable residue is small and portal-only: Cloud Policy Service, some Copilot admin toggles. Corroborated against a real-world 4-variant Copilot IaC build (bicep-max / terraform-max / cascade-max / powershell-only).
