What an exposed Terraform state file actually puts at risk.

A sober assessment of the worst-case exposure of the PingOne Terraform state file — assuming the state file is obtained by an attacker, across all environments, with best practices ignored. The aim is to replace an unbounded fear with a bounded, evidence-based picture of what an attacker could and could not do.

Assessment summary

Straight answer, no hand-waving: with the PingOne Terraform provider today, real secrets land in the state file in plaintext (there's no write-only support), and some of them are catastrophic if leaked — a worker-app admin secret is full IdP takeover; an imported signing key forges any user's token; a Twilio token reads OTP bodies. And rotating in PingOne doesn't save most of them — the dangerous ones are owned by external systems (Twilio, the CA, your mail relay, AD), and the damage is instant, so a rotation window barely helps. So the honest control isn't "rotate it" — it's keep the dangerous ones out of Terraform entirely. Almost every catastrophic secret is an input we supply, so it belongs in the vault, never in state. The few PingOne forces into state (worker/app secrets, the gateway JWT) are exactly the ones PingOne-rotation does instantly kill. Do that discipline and it's bounded; skip it and it's a crown-jewel breach. This brief shows every secret, what it actually does, and where the line is.

What the artifact is

A configuration inventory — that, with this provider, also holds credentials.

Terraform's state is a JSON record of what it manages: resource IDs, names, and settings — a current picture of the configuration. It's meant to hold configuration, not secrets. But the PingOne provider has no write-only or ephemeral support (verified against v1.20.0), so any secret you manage in Terraform is written to state in plaintext. Sensitive: true only masks it in CLI output — the value is still in the file.

Contents — the honest worst case

Yes, secrets land in state. Here's the list — not a reassurance.

First, the framing: this is a maximalist "use every PingOne feature" deployment — deliberately worse than what we're actually building. Even then, it would put ~20–30 distinct secrets into state, in plaintext:

+ Application & worker secrets Every OIDC / worker-app client secret (pingone_application_secret) and custom OAuth resource secret.
+ Directory & network credentials The LDAP bind_password, gateway service-account password, RADIUS shared secrets, and the PingOne-issued gateway credential.
+ Every external-IdP secret Google, Microsoft, Facebook, LinkedIn, Apple, and generic-OIDC client secrets and signing keys — one per configured provider.
+ Messaging & crypto material SMTP password / OAuth token, SMS & voice provider tokens, MFA push keys (APNS .p8, FCM JSON), imported PKCS#12 key material, custom-domain TLS private keys, the reCAPTCHA secret, and any initial user passwords set through Terraform.
− The one that matters most is not here The admin / API credential Terraform uses to authenticate to PingOne is passed to the provider at run time — never written to state. So a stolen state file cannot be used to reconfigure or take over your tenant.

Mitigations — how we shrink that list to near-nothing

The dangerous ones don't need to be in Terraform at all.

1

Keep the crown jewels out — the real fix

Nearly every catastrophic secret is an input we supply — the Twilio token, the TLS key, SMTP, external-IdP secrets, the LDAP bind password. None need to be in Terraform: keep them in the Secret Vault / HSM, referenced out-of-band. That removes every externally-owned, rotation-resistant secret from state at once.

2

The few PingOne forces in → instant rotation

Only a handful must be in state, because PingOne generates them — worker / app secrets and the gateway JWT. Those are exactly the ones a PingOne-side rotation instantly kills. Rotate every deployment — ~5 minutes automated (≈15 with CAB); a leaked copy is dead the moment we rotate.

3

Don't lean on rotation alone

For the externally-owned secrets, rotating in PingOne doesn't help — they must be rotated at the source. And for instant-damage secrets, a 24-hour window is 24 hours of exposure. So the discipline is keep them out (mitigation 1), not "rotate faster."

Attack path — worst case, traced to its end

An attacker holds the entire state file — secrets included. Where does it actually lead?

Now strip away every mitigation above — assume we did none of it, and all ~20–30 secrets are sitting in the file an attacker just stole. This is the ceiling:

1

They read everything — the config and the secrets in it.

The full map of the estate, plus the couple-dozen credentials listed above.

They hold config + a set of credentials. Here is why that is still contained.
2

They try to take over the tenant — and cannot.

The admin credential Terraform authenticates with is not in state, so they cannot reconfigure or seize PingOne wholesale. The worst they hold are individual, scoped secrets.

No tenant takeover.
3

They try the leaked LDAP bind password — and hit a wall.

It authenticates to the on-prem directory, not to PingOne (the gateway uses a separate, revocable credential), and that directory isn't reachable from the internet — useless without a foothold inside the corporate network.

And if they force their way on-network anyway? The account follows least privilege: it is read-only, scoped to the user subtree. The ceiling is reading the user list and the handful of attributes it's permitted (name, email, group membership) — pure reconnaissance. They cannot modify anything, cannot read passwords (the directory never returns password material over LDAP — not even to admins), cannot leave that OU, and cannot reach PingOne.

Ceiling: read-only recon of the user directory — and only for an attacker already inside the network.
4

The individual secrets? Each has its own blast radius — the matrix above is the full accounting.

They range from catastrophic (a worker-app admin secret, an imported signing key, the Twilio token) to trivial (reCAPTCHA). But the catastrophic ones are all input secrets we keep out of state; the ones we can't keep out (PingOne-generated) are exactly the ones an instant PingOne rotation kills.

Bounded — if the crown jewels are kept out of state.
5

And none of this happens unless they first beat the controls.

Getting the state file at all means defeating what makes it a top-tier secret — encryption, access logging, privileged-only access — plus, for anything live, the vault and a pipeline identity. Clear all of that and the organization is already lost, state file or not.

The state file was never the soft spot.
Blast radius, even in the worst case

Bounded to the protected application — not the organization.

◐ Worst case yields

Reconnaissance of the protected application's authentication configuration and, only if built without controls, a credential that other measures already neutralize.

✓ Does not reach

Downstream business data. PingOne is scoped to that application's authentication; the state file is a configuration map, not a data path.

✓ Does not cause

An operational outage. Reading a configuration inventory does not alter or stop the running service.

Comparative exposure

Handled correctly, the state file is less exposed than the current manual process.

Terraform state

The secrets sit in one controlled place — encrypted at rest, access-logged, reachable only by the pipeline identity, and rotatable in bulk. You know exactly what is where, and can rotate all of it on demand.

Manual configuration (ClickOps)

The same secrets are hand-carried by a person through the console — pasted who-knows-where, with no gate, no record of what went where, and no clean way to rotate. Nothing to encrypt, nothing to audit.

Controls applied — defense in depth

The state file is treated as sensitive regardless of its contents.

  • Isolated backend, its own credentialsA dedicated store only the pipeline identity can reach — demonstrated on GitLab.
  • Encrypted at rest, every access loggedOn Azure Blob: AES-256 encryption that can't be disabled; keyless Entra-only access (no storage key to steal); and with diagnostic logging on, every read / write / delete recorded with the calling identity, operation, and timestamp. Versioning, soft-delete, and WORM immutability protect the history.
  • Commit-bound production changesProduction changes only via a CAB-approved ServiceNow record bound to the exact commit, by an authorized person.
  • Access only through the privileged identityProperly configured, the state is reachable only through the backend's own privileged (super-admin) identity — a leaked pipeline token, stale credential, or random attacker gets nothing.
Conclusion

Keep the crown jewels out — then it's a hardened, rotatable secret store.

The honest finding: some of these secrets are catastrophic, and rotation alone won't save most of them. But almost every catastrophic one is an input we control — so the discipline is simple and decisive: keep the dangerous secrets in the vault / HSM, never in Terraform; the few PingOne forces into state are exactly the ones a PingOne-side rotation instantly kills; and the state file itself is encrypted, access-logged, and reachable only by the privileged identity. Do that, and the residual exposure is bounded to the protected application with no tenant takeover. Skip it, and it's a crown-jewel breach — which is precisely why it is not optional.
