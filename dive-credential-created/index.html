2Where the salt actually is

This is the whole of what the authorization server stores — one 60-character string, sliced live from the real hash rather than transcribed. There is no salt column. There is no external key, and no pepper. The salt is already in the string, in the open, and that is not a mistake.

A salt is not a secret. Its job is to make two identical secrets hash differently, so one cracked value does not unlock every other row, and so precomputed tables are useless. It defeats bulk attacks, not targeted ones — which is why publishing it alongside the digest costs nothing. Storing it separately would buy no security and add a way to lose it.

3The same secret, hashed three times

All three of these are hashes of the identical secret, produced seconds apart. All three verify against it. Every character after the cost is different — because each run drew a fresh salt.

bcrypt is not deterministic, so "the server hashes what you sent and compares it to what it stored" cannot be how verification works — it would fail every time. That description invites exactly the right question, then why do two hashes of one secret differ?, and has no answer.

4So what does verification actually do

The stored string is not just an output — it is a recipe. Verification reads the parameters back out of it and re-runs the same derivation with them.

Step 1 · read
Extract cost and salt
Parse them out of the stored string. This is why the format is public and self-describing.
Step 2 · derive
Re-run bcrypt
Hash the presented secret with that cost and that salt — not a fresh one. Same inputs, same output.
Step 3 · compare
Constant time
Compare the two digests without short-circuiting on the first differing byte, so the time taken leaks nothing about how much matched.
Step 4 · answer
One bit
True or false. At no point was the stored secret recovered, because it is not in there to recover.
Nothing is ever decrypted. bcrypt is a one-way function, not a cipher — there is no key that turns the stored string back into the secret. "We do not need salting unless we want to decrypt the password" inverts it: you can never decrypt it, and the salt is what makes the one-way direction safe to store.

5The cost factor is the point of using bcrypt at all

The 10 in the string is a base-2 logarithm: each step up doubles the work. That knob is why a 1999 algorithm is still usable in 2026 — you raise it as hardware gets faster. Measured on this machine just now:

Against this particular secret, the slowness is not what saves you — the entropy is. A 256-bit random value has no dictionary and no pattern to exploit, so no realistic number of guesses gets there whether each one costs 50 ms or 50 ns. The hashing is there for a different threat: if the credential store is read by someone who should not have it, what leaks is 60 characters that authenticate nothing. Slow hashing is what keeps that true even for the human-chosen secrets that inevitably end up in the same table.

6Where this comes from

RFC 6749 §2.3.1 · Client Password — establishes that a client may hold a secret and authenticate with it. Read first-party 2026-08-06.
RFC 4086 (BCP 106) · Randomness Requirements for Security — §3 Entropy Sources, §6 Pseudo-random Number Generators. Why the generator must be a CSPRNG and not a convenience rand().
OpenBSD crypt_newhash(3) — "the value of rounds can be between 4 and 31 and specifies the base 2 logarithm of the number of rounds." The cost semantics, first-party.
Provos & Mazières, USENIX 1999 · A Future-Adaptable Password Scheme — the original bcrypt paper; the adaptable cost factor is its whole thesis.
ours, not a spec
No RFC requires client secrets to be hashed. RFC 6749 leaves storage to the implementation entirely. Hashing them is our own decision, borrowed from password practice — worth saying out loud so nobody goes looking for the clause.
ours, not a spec
No pepper. A pepper is a secret added to every hash, and it needs its own custody — which is the same problem as protecting a signing key, moved somewhere less visible. Its absence here is a choice, not an oversight.
Elsewhere — someone else on hashing Password Storage Cheat Sheet· OWASP Cheat Sheet Series Backs two of this page's numbers from outside it: bcrypt at a work factor of 10 or more, and that you do not generate or manage salts by hand because the library does it internally. Read it for the caveat this page does not cover either — bcrypt's 72-byte input limit. It stops short of §2's actual claim that the salt sits inside the output string; that part stays first-party here, read out of a real implementation rather than borrowed.
