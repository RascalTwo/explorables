1Five gates, and one of them is load-bearing

Pick a token and watch it go through. The signature checks below are real — the page holds the actual RSA public key that signed the genuine token and runs crypto.subtle.verify in your browser. The forgeries fail because they are genuinely invalid, not because a script says so.

2Trap one — trusting a claim before the signature

Until gate 3 returns true, the payload is not data. It is an attacker's suggestion, base64-encoded. Anyone can produce a string whose payload says whatever they like; that costs nothing and requires no key.

What the mistake looks like

Decoding the payload early — to log the caller, to pick a tenant, to route the request, to fetch a record — and then verifying afterwards. Or verifying in a filter that some paths do not run through.

const claims = decode(token);      // ← attacker-controlled
log.info("caller", claims.sub);
const tenant = load(claims.tenant); // ← already too late
verify(token);

Why it bites even when the check is there

The damage happens before the rejection. A database lookup on an unverified identifier, a log line poisoned with attacker-chosen text, a cache keyed by a forged tenant — all executed, all on input that was about to be thrown away.

RFC 7519 §7.2 puts the signature at step 7 of ten and does not even extract the claims set until step 10. That ordering is the specification's answer to this.

3Trap two — letting the token choose its own algorithm

The header is unprotected. It says alg, and a verifier that simply does what it says is asking the attacker how to check the attacker's own work.

alg: none

The header claims the token is unsigned, and a library that honours it "validates" a token with no signature at all. RFC 8725 §2.1: "The algorithm can be changed to 'none' by an attacker, and some libraries would trust this value and 'validate' the JWT without checking any signature."

RFC 9068 §2.1 closes it for access tokens outright: they MUST NOT use none.

RS256 → HS256 confusion

Subtler and more dangerous. Change alg to HS256 and sign with the public key as the HMAC secret. A verifier that picks its algorithm from the header hands the public key to an HMAC function — and the public key is, by design, something the attacker already has.

RFC 8725 §2.1 describes exactly this: "some libraries would try to validate the signature using HMAC-SHA256 and using the RSA public key as the HMAC shared secret."

The fix is one line, and it is a configuration, not a check. The verifier declares which algorithms it accepts, before it ever looks at a token — RFC 8725 §3.1: "Libraries MUST enable the caller to specify a supported set of algorithms and MUST NOT use any other algorithms when performing cryptographic operations." The alg in the header is then only useful for confirming what you already decided.

4None of that touched a database

This is what explains most of the confusion about tokens, in both directions.

Why it is fast

Verification is arithmetic over bytes that arrived in the request, plus a public key the server already had. No lookup, no network call, no shared session store. A resource server can accept traffic from an authorization server it has never contacted, and scale horizontally without any coordination.

Why revocation does not work the way people expect

Nothing is consulted, so there is nothing to change. Deleting the client, disabling it, or rotating its secret does not stop a token that was already issued. Those actions stop the next token from being minted. The one in flight keeps working until exp.

That is the trade, and it is why the lifetime is short: expiry is the revocation mechanism.

If that window is unacceptable, the answer is not a database lookup on every request — that gives back the property the design was bought for. It is either a shorter lifetime, or introspection for the few endpoints that genuinely need immediate revocation, chosen deliberately and priced. Rotating the signing key is the blunt version: it invalidates every outstanding token at once.
