The failure cap — why the counter hangs off the credential

A hundred guesses from a hundred addresses. Two counters watch the same traffic and disagree completely.

This is the control that guards the moment drawn in the client credentials flow — the client presenting its secret to the token endpoint. How that secret is made and stored is How a credential is created securely; what a stolen one buys an attacker is What an attacker has to steal.

1Same attack, two counters

An attacker is guessing the secret for one client_id. Switch how they source the traffic and watch what each counter does. Both counters see every single attempt — the only difference is what they count it against.

"Consecutive" is scoped to one client_id. The counter is a value on that credential's own row: it goes up on a failed attempt against that identifier and back to zero the moment one succeeds. Failures against a different client_id increment a different counter and never mix — which is also why an attacker cannot burn down a caller's counter without knowing which caller to aim at.

2What the standard actually asks for

The requirement is specific about the key, and it is the part most often implemented wrongly — as volumetric throttling, which counts something else.

ControlCountsWhat it stops, and what it doesn't
Rate limitingrequests per source, over time Stops one address flooding you. Does nothing about distributed guessing — an attacker with a hundred addresses never trips it, and a legitimate caller behind a shared egress address can trip it by accident.
Failure capconsecutive failures per client_id, reset on success Stops guessing regardless of where it comes from. Says nothing about volume, so it is not a throttle and does not protect against resource exhaustion.

NIST SP 800-63B-4 §3.2.2 Rate Limiting (Throttling) requires limiting "consecutive failed authentication attempts using a specific authenticator on a single subscriber account to no more than 100 by disabling that authenticator." Progressive delays and bot-detection challenges are an additional MAY, layered on top — not a substitute for the cap.

3What happens at the cap

The standard names exactly one verb, and it is disable. Delete is not an alternative it offers — delete comes from somewhere else entirely.

Two specifications describe how a client gets created and managed over an API. RFC 7591, OAuth 2.0 Dynamic Client Registration Protocol, covers registering one. RFC 7592, OAuth 2.0 Dynamic Client Registration Management Protocol, covers what you may do to it afterwards — read, update, delete. In 7592, delete means deprovisioning a client that is finished with, not locking out one that is under attack. Answering the cap with it is a substitution, and it is worth saying so in those words: a reviewer who is told the standard offered both will check.

What the standard says

Disable

The authenticator stops working and the identifier survives. Somebody with authority turns it back on, and the credential that was already distributed keeps working.

Recovery is an administrative act. Nothing has to be re-issued, re-collected or re-configured at the caller's end.

What RFC 7592 offers instead

Delete

The row goes. There is no disabled state to return from, so hitting the cap is operationally identical to a revocation — a new identifier and a new secret, issued and distributed from scratch.

That is a defensible answer. It is not the same answer, and it should be stated as a substitution rather than presented as compliance.

4Neither verb is free — so the choice is which one to build

The instinct after §3 is that this is a gap in the design: the standard wanted disable, the design only had delete. That framing is wrong in a way worth correcting, because delete was not sitting there either. It was written by hand, to the spec's shape, because the framework does not provide it. Both verbs cost the same kind of work.

The framework you build onTypically create and read, and no further — and often switched off by default, because dynamic registration is a feature most deployments never turn on. Update and delete are commonly absent, and disable is absent everywhere, so the verb you need is yours to write either way.

This is not a hole in the specifications. Client lifecycle was never in scope for the protocol — whether a client may currently authenticate is a policy decision, the same category as which scopes it may request or which grants it is allowed, and none of those are in the RFCs either. Off-the-shelf authorization servers all ship an enabled/disabled flag as a product feature; that surface belongs to the vendor, not the standard. An organisation that builds its own authorization server inherits it.

Disable — what it takes

A predicate, not a mechanism

A flag on the client record — which can ride in whatever settings blob the framework already persists, so nothing has to be subclassed — plus a lookup that returns nothing when the flag is set.

The enforcement is already written. If the lookup yields nothing, the token endpoint behaves exactly as it does for a client that never existed, down a path the framework already ships and already tests. What you are adding is a filter on a query, not an authentication decision.

Delete — what it took

A whole verb, by hand

An endpoint, the removal itself, and the authorisation around it — all written to the spec's shape rather than invented, precisely because the framework had nothing to call.

Which is the useful comparison: the more destructive verb was the more expensive one to build, and it is already shipped. Adding the reversible one is the smaller job of the two, and it is the one the standard actually asked for.

None of this is a library falling short. The management spec is Experimental and its operations are optional by design; dynamic registration itself is a feature most deployments never enable, which is why implementations stop where they do. Low demand for an optional feature is a better explanation than an oversight, and it is the honest one to give a reviewer who asks why this was hand-written.

And the half that is not code at all

Writing the verb is the cheap part

Whichever verb gets built, it creates a state somebody has to notice. If nothing tells the caller, the failure they see is indistinguishable from a wrong secret — and the first thing they will do is retry, which is the traffic that stopped them in the first place.

So it needs a reason recorded against the record, a signal to whoever operates the calling system, and a documented way back. Skipping that turns a security control into an unexplained outage, and it is the part no library was ever going to provide.

Worth being clear about what either verb buys, too: it stops the caller getting a new token. Tokens already issued are self-contained and keep working until they expire, so containment is bounded by the token lifetime either way.

5The cap is a weapon if the identifier is guessable

Anything that disables an account on failed attempts can be pointed at somebody else's account. This is the standard objection to lockout, and it has a structural answer.

If the identifier is…Then the cap is…
Sequential, or derived from a name A denial-of-service button. Anyone who can guess or enumerate identifiers can lock out any caller they choose, by failing on purpose. The control meant to protect the account becomes the cheapest way to take it down.
A random value with no meaning Hard to aim. An attacker cannot target a caller they cannot name, and an identifier they already know usually means they have the secret too — at which point the cap is not the thing standing between them and the data.

This is the reason to generate identifiers randomly rather than derive them from anything meaningful, and it is worth recording as the rationale — a design that randomises them for tidiness gets the protection by accident and can lose it in a refactor that nobody flags.

Elsewhere — both of the above, independently Authentication Cheat Sheet· OWASP Cheat Sheet Series Reaches §1 and §4 of this page from a different direction and states both plainly: "the counter of failed logins should be associated with the account itself, rather than the source IP address, in order to prevent an attacker from making login attempts from a large number of different IP addresses", and "care must be taken to prevent it from being used to cause a denial of service by locking out other users' accounts." Its mitigation is a self-service recovery path — worth reading, because a machine-to-machine credential has no such path, and that absence is exactly why §3's delete-versus-disable choice costs more here than it would for a human login.
