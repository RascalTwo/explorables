The mental model

You already run containers.
Now run them on a fleet that heals itself.

Docker Compose answers "run these containers together on this one machine." Kubernetes answers "keep these containers running, the right number of them, reachable, across a cluster of machines — and put them back when something dies."

The single biggest shift: Compose is imperative-ish — you bring it up, you bring it down. Kubernetes is declarative + reconciling. You submit the desired state ("I want 3 replicas of this image, reachable on port 80"), and a control loop continuously makes reality match it. Kill a container and it comes back — not because you restarted it, but because reality drifted from the spec.
docker compose up

One YAML file. One host. services, networks, volumes. You own the box.

kubectl apply -f

Many typed objects. A scheduler places them on nodes. A controller keeps them alive. You own the intent.

A familiar 3-service compose file

2 · The mapping

      
Every Compose idea becomes a Kubernetes object

      
Same app, re-expressed. Hover a Compose concept on the left to see which Kubernetes object absorbs it.

      

        

        

        

      

      

        The mental rule: a service: in Compose is never one thing in Kubernetes.
        It fans out into a Deployment (how many, which image, self-healing),
        a Service (a stable in-cluster address that load-balances across the copies),
        and — if it faces the internet — an Ingress (host/path routing + TLS).
        Config and secrets are lifted out of the workload into ConfigMap/Secret so the same image runs unchanged in every environment.

4 · The YAML sprawl

      
One compose file → a pile of manifests

      
That single docker-compose.yml becomes roughly a dozen Kubernetes manifests once you account for every service's Deployment, Service, config, secrets, and the Ingress. This is real and it's the pain Helm exists to solve.

      

        

          before — 1 file
          
# docker-compose.yml
services:
  web:   # …
  api:   # …
  db:    # …

# 1 file. ~30 lines.
# `docker compose up` and done.

        

        

          after — raw kubernetes
          
# k8s/
web-deployment.yaml      # 40+ lines
web-service.yaml
api-deployment.yaml
api-service.yaml
api-configmap.yaml
api-secret.yaml
db-statefulset.yaml
db-service.yaml
db-pvc.yaml
ingress.yaml
# …same values copy-pasted across files

        

      

      

        Now multiply by environments. dev wants 1 replica and a *.dev host;
        prod wants 4 replicas, real TLS, bigger memory limits. With raw YAML you either keep
        3 near-identical copies of every file or hand-edit before each deploy. Both rot. Enter Helm.
      

    


    
    

      
5 · Why Helm

      
Helm is "docker-compose-meets-templating", for Kubernetes

      
Helm packages that pile of manifests into one versioned, parameterised unit called a chart.
      Think of it as: the manifests become templates, the per-environment differences move into one values.yaml,
      and helm install renders templates + values into final manifests and applies them — like docker compose up, but for a templated bundle.


      

        

          
ANALOGY

          

            
Docker imagereusable artifact

            
→ Helm chartreusable app package

            
docker run -e VAR=…params at runtime

            
→ helm install -f valuesparams at deploy

            
Docker Hubimage registry

            
→ chart repo / OCIchart registry

          

        

        

          
CHART ANATOMY

          

myapp/

├── Chart.yaml      # name + version of the chart

├── values.yaml     # default knobs (replicas, image, host…)

├── templates/

│   ├── deployment.yaml # manifest w/ {{ }} holes

│   ├── service.yaml

│   └── ingress.yaml

└── charts/         # sub-charts (e.g. postgres dep)
          

          
A chart is just this directory, tarred. helm install web ./myapp -f prod.yaml renders it and applies the result to the cluster.

Recap

      
The whole arc in five sentences

      
    
        
  1. Compose runs containers together on one host; you manage the process.
    2. 
        
  2. Kubernetes runs them across a cluster and reconciles reality to a declared spec — so things self-heal.
    3. 
        
  3. One Compose service explodes into typed objects: Deployment (how many / which image), Service (stable address + load-balancing), Ingress (internet routing), ConfigMap/Secret (config out of the image).
    4. 
        
  4. Raw manifests duplicate across environments and rot.
    5. 
        
  5. Helm templates those manifests + one values.yaml into a versioned, installable package — docker compose up energy, cluster-scale.
