PingOne Vanity URLs (“Custom Domains”)

Your brand on the login screen instead of pingone.com — what moves, what stays, and how it’s wired up.

1 What it is & why anyone cares

A vanity URL routes your own domain to PingOne’s hosted auth screens, so users never see “pingone” in the address bar.

🔒 auth.example.com/<envID>/as/authorize
▸ show default
Users land on your branded sign-in page — same PingOne service underneath, different name on the door.
🛡️ Brand & anti-phishing
Users authenticate against a domain they recognize — not a third-party vendor host.
🍪 First-party cookies
Session cookies set on your domain — matters for SSO behavior & browser tracking-prevention.
✨ Seamless experience
Login / registration / MFA / self-service screens feel like part of your own site.
✅ Allow-listing
Easier for corporate IT / email filters to trust a first-party domain than a vendor one.

2 What it looks like

Almost always a subdomain you own — auth. / login. / id. / sso. — fronting the PingOne auth path.

auth.example.comyour vanity host/<environmentID>PingOne env/as/authorizeauth endpoint · unchanged
⚠ One custom domain per environment. dev / test / prod are separate PingOne environments → separate domains (e.g. login.dev.acme.com vs login.acme.com). Wildcard & SAN certs are supported.

3 What moves under your domain vs. what stays on Ping

The crux. The vanity domain covers the end-user auth edge only — not the admin or config planes.

✅ Moves under your domain

https://auth.example.com/…
Authorization & token endpoints/as/authorize, /as/token — the OIDC / OAuth flow URLs
Hosted login / registration / MFA / password resetincluding DaVinci flows rendered through PingOne
Self-service “MyAccount”/myaccount end-user portal
Branding assets on those screenslogos / CSS served as part of the flow

⛔ Stays on Ping’s domains

*.pingone.com / *.pingidentity.com
PingOne Admin Consoleexplicitly NOT supported on custom domains — admins keep the Ping console URL
Management APIapi.pingone.com — the config/control plane Terraform & your backend call
Regional auth baseanything you haven’t explicitly fronted with the vanity host
Mental model: the vanity domain is the end-user authentication edge, not the config / management plane. If it’s a screen a customer sees, it can move; if it’s an admin or an API, it doesn’t.

4 How it’s set up — a 3-party handshake

PingOne fronts custom domains through Cloudflare (post-2025-03-17). Setup is a handshake between PingOne, your DNS, and a certificate authority. Click a step to trace it.

    5 What you touch in other services

    Beyond PingOne, a vanity URL reaches into three systems.

    ServiceWhat you do there
    Your DNS provider
    Route53 / Cloudflare / Azure DNS    		 Add the CNAME (auth.example.com → canonicalName) + any TXT verification record. ⚠ With a reverse proxy / WAF in front, Cloudflare can’t be your authoritative nameserver.
    Certificate Authority / PKI
    DigiCert / Let’s Encrypt / internal CA    		 Issue the cert for auth.example.com; hand PingOne the key + cert + intermediate chain (PEM, RSA-2048 / ECDSA-256 min, no self-signed). Renewal is the #1 footgun — expired cert = broken login.
    Your relying apps / OIDC clients Update issuer / authority, authorization_endpoint, token_endpoint, redirect & logout URIs to the vanity host so tokens are issued & validated against the new domain.

    6 Via Terraform (PingOne provider)

    Two resources, split so DNS slots in between: create the domain → CNAME the computed canonical_name → upload the cert.

    # 1 — create the domain; exposes the computed canonical_name for your CNAME
resource "pingone_custom_domain" "auth" {
  environment_id = var.environment_id
  domain_name    = "auth.example.com"
}

# 2 — feed pingone_custom_domain.auth.canonical_name into your DNS CNAME here
#     (aws_route53_record / cloudflare_record / azurerm_dns_cname_record)

# 3 — upload the cert once DNS resolves (chain + cert + private key, all PEM)
resource "pingone_custom_domain_ssl" "auth" {
  environment_id                     = var.environment_id
  custom_domain_id                   = pingone_custom_domain.auth.id
  certificate_pem_file               = file("cert.pem")
  intermediate_certificates_pem_file = file("chain.pem")
  private_key_pem_file               = file("key.pem")
}
    ⚠ Confirm exact argument names on the provider registry before pasting into prod HCL — the shape (two resources, canonical_name computed, cert as three PEMs) is solid; the precise attribute spellings are worth a 30-second check.
