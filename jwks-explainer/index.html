JWKS distributes keys, not certificates

A JSON Web Key Set is how an authorization server publishes the public half of its signing key so that anyone can check the tokens it mints. It looks like a certificate-distribution problem. It is not one — and every instinct carried over from PKI is one whole concept too heavy.

A JWK is a bare public key with a name on it. No subject. No issuer. No validity window. No CA signature. No chain. Nothing to install, nothing to expire, nothing to store on a dedicated server.

Generic throughout: an authorization server that signs, a client that carries a token, a resource server that verifies. No product names, no network zones. Every factual claim below is cited to the RFC section that makes it — titles quoted verbatim.

kty

Key type. Which family of key this is — here, RSA. It determines which other members are even meaningful. RFC 7517 §4.1 · “‘kty’ (Key Type) Parameter”

n

The modulus. This is the public key. Those 342 characters are one very large integer, base64url-encoded — “represented as a Base64urlUInt-encoded value.” It is not a pointer to a key, or a wrapper around one. It is the number. RFC 7518 §6.3.1.1 · “‘n’ (Modulus) Parameter”

e

The public exponent. AQAB decodes to 65537, the near-universal RSA exponent. Together, n and e are the entire public key — nothing else on this page is key material. RFC 7518 §6.3.1.2 · “‘e’ (Exponent) Parameter”

alg

The algorithm this key is used with. RS256 is RSASSA-PKCS1-v1_5 with SHA-256, which requires “a key of size 2048 bits or larger.” RFC 7518 §3.3 · “Digital Signature with RSASSA-PKCS1-v1_5”

kid

The selector — a name, and nothing more. An opaque label a verifier matches on to pick this key out of the set. Every question about rotation is answered by this one member. Note the value here is a date; it can be any string. RFC 7517 §4.5 · “‘kid’ (Key ID) Parameter”

use

Signing or encryption. Commonly seen as "use":"sig", but absent from the specimen above — it is not required. RFC 8414 makes it mandatory only when one key set carries both signing and encryption keys. RFC 7517 §4.2 · “‘use’ (Public Key Use) Parameter”

A JWK Set is just a wrapper around a list. {"keys": [ … ]} — “the value of the ‘keys’ parameter is an array of JWK values.” The plural is load-bearing; §6 is why. RFC 7517 §5 “JWK Set Format”, §5.1 “‘keys’ Parameter”

02 What an X.509 certificate has that a JWK does not

This is the whole point of the page. A certificate is a public key plus an assertion about who it belongs to, signed by someone you already trust. A JWK keeps the key and drops the assertion — so every field that made a certificate a certificate is simply not there.

X.509 certificate field What it asserts In a JWK
SubjectRFC 5280 §4.1.2.6 The identity this key belongs to — a distinguished name, a hostname. — no such member
IssuerRFC 5280 §4.1.2.4 The certification authority that vouched for the binding. — no such member
ValidityRFC 5280 §4.1.2.5 “The period of time from notBefore through notAfter, inclusive.” — no such member. A JWK never expires; it is withdrawn from the set.
SignatureRFC 5280 §4.1.2.3 The CA’s signature over everything above — what makes it verifiable. — no such member. Nothing signs a JWK.
Serial NumberRFC 5280 §4.1.2.2 A unique number per CA, the handle used for revocation (CRL, OCSP). — no such member. No revocation protocol exists.
Certificate chainRFC 5280 §6 path validation The walk from this certificate up to a trust anchor you already hold. — nothing to walk
Subject Public Key InfoRFC 5280 §4.1.2.7 The algorithm identifier and the public key bits themselves. Present — this is kty, alg, n, e. This row, and only this row.

A JWK is, in effect, one field of a certificate — the public key itself — with a name attached so you can ask for it later. Six of the seven rows above are the parts a JWK deliberately does not have. There is no file to install, no expiry to diary, and nothing to store on a dedicated server, because there is no certificate.

Yes, a JWK may carry a certificate chain — and almost never does. RFC 7517 defines x5c (§4.7, “‘x5c’ (X.509 Certificate Chain) Parameter”) and x5t (§4.8, “‘x5t’ (X.509 Certificate SHA-1 Thumbprint) Parameter”) for exactly this. Of both the specification says: “Use of this member is OPTIONAL.” They are absent from the specimen in §1, absent from the typical authorization server’s key set, and nothing in the verification path in §5 consults them. Knowing the option exists is not the same as it being implied.

Then where does trust come from? This is the fair question a PKI reader asks next, and the answer is the honest one: from the transport and the configuration, not from a signature. You trust a key set because you fetched it over HTTPS from a URL you deliberately configured — RFC 8414 requires that jwks_uri “MUST use the ‘https’ scheme.” The TLS certificate on that host is doing the PKI work. The key set itself carries no trust of its own and does not need to.

03 Only the public half is ever published

The private key never leaves the issuer. Publishing the public half is not a concession or a risk to be managed — it is the entire design. Anyone may verify; only the issuer may sign.

There is nothing secret on the JWKS endpoint, so there is nothing to protect there. Every byte it serves is designed to be world-readable. Treating it as sensitive is the second thing PKI intuition gets wrong, and it leads directly to §4.

04 The endpoint needs no authentication — and cannot sensibly have any

This is not a relaxation of a control. It is a structural impossibility: requiring a token to fetch the key that validates tokens is circular.

Empirically, this is how these servers are probed. The conventional liveness check is a plain fetch with no credentials at all — wget -qO- http://host/oauth2/jwks | grep -q keys. If the endpoint required a token, every health check, every verifier cold start, and every new deployment would deadlock.

05 How a verifier actually uses it

A token in transit is three base64url segments separated by dots. The kid that selects the key lives in the first one — readable before anything has been verified, which is exactly what makes key selection possible.

4 · Now read the claims

Only after the signature holds do iss, aud and exp mean anything.

A JWT is signed, not encrypted — anyone holding one can read every claim. The panels above are not a debugging view; that is what the token is. Base64url is an encoding. RFC 7519 §12, “Privacy Considerations,” is explicit that this is your problem to manage: “A JWT may contain privacy-sensitive information. When this is the case, measures MUST be taken to prevent disclosure of this information to unintended parties. One way to achieve this is to use an encrypted JWT.” Decide what goes in a token accordingly.

Signature first, then claims. Until step 3 succeeds, iss, aud and exp are attacker-controlled bytes. A verifier that reads iss to decide which issuer to trust, before checking the signature, has inverted the order and trusts the attacker’s answer.

Scope boundary. This page ends at the signature. Which claims a resource server should then insist on — audience, expiry, scope, issuer matching — is a separate subject and is not key distribution.

06 Rotation, and why it is a set

This is the cleanest answer to “how do you rotate?”, and it is the reason the plural in JWK Set is load-bearing: for a window, the endpoint publishes both keys.

Before
{"keys": ["2011-04-29"]}

One key. Every token in circulation carries kid: "2011-04-29".

Overlap window
{"keys": ["2026-08-06","2011-04-29"]}

Both published. New tokens are signed with the new key; tokens minted before the switch still name the old kid and still select successfully. No token is ever orphaned.

After the last old token expires
{"keys": ["2026-08-06""2011-04-29"]}

The old key is dropped from the set. Nothing was revoked and nothing expired — it simply stopped being published.

The overlap only has to outlast the longest-lived token, not the longest-lived client. Because selection is by kid and not by recency, the window is bounded by token lifetime — typically minutes. Compare the certificate equivalent, where a rollover is coordinated against every relying party’s trust store.

All of that is planned rotation. An emergency is a different operation. The overlap window depends on continuing to publish the old key — which is precisely what you cannot do when that key is the thing that leaked. In an incident it has to be withdrawn at once, so there is no overlap, and every legitimate outstanding token dies alongside the attacker’s. What each containment lever actually costs is drawn out in Turning it off; what an attacker gains from each secret is in What an attacker has to steal.

07 Caching, and the behaviour worth knowing

Verifiers cache the key set — five minutes is a common default. The behaviour that makes rotation painless is what happens on a kid the cache has never seen: an immediate re-fetch and a re-select inside the same call. The request that triggers the refresh succeeds. It does not fail first.

The library’s own comment at line 464 is “Refresh the JWK set if the sought key ID is not in the cached JWK set,” and the method ends on “Repeat select, return final result.” The caller sees one successful verification, not a failure followed by a retry.

Do not shorten the cache TTL to chase rotation. The unknown-kid path above already handles it, on the first request that needs it. A shorter TTL adds constant background traffic to solve a problem that is already solved.

Do not disable the cache. That makes the authorization server a synchronous dependency of every single API request — an availability coupling that undoes the entire reason for using self-contained tokens.

This is a major identity provider publishing the same rules as operational guidance, which is a different and stronger kind of evidence: cache keyed on kid, refresh on a timer, and refresh on the hot path when a token arrives with a kid nobody knows — rate-limited so it cannot be used to hammer the endpoint. It also states §06's point outright — "there's always more than one valid key available", and applications supporting only a single signing key are "inherently less secure and less reliable."

08 Discovery is optional

An authorization server may publish metadata at /.well-known/oauth-authorization-server describing itself, including where its key set lives. This is a convenience, not a dependency.

jwks_uri is an OPTIONAL member. RFC 8414 §2, “Authorization Server Metadata,” defines it verbatim as: “OPTIONAL. URL of the authorization server’s JWK Set [JWK] document. The referenced document contains the signing key(s) the client uses to validate signatures from the authorization server. This URL MUST use the ‘https’ scheme.”

And the specification contemplates skipping discovery entirely. RFC 8414 §1, “Introduction”: “In some cases, its issuer identifier may be manually configured into the client.” A verifier pointed straight at a key set URI never fetches the metadata document at all — and nothing in §5 or §7 above depends on it.
