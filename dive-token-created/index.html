1Two halves of one key, and only one of them moves

Signing is asymmetric, and that asymmetry is the entire reason this scales. The authorization server can prove it minted a token to parties it has never met, without ever sharing anything that would let them mint one.

Never leaves

Private key

Signs. Held only by the authorization server. Anyone who obtains it can mint tokens that every resource server will accept, so its custody is the security of the whole system.

ONE KEYPAIR
Published deliberately

Public key

Verifies. Handed out freely to anyone who needs to check a token. Publishing it costs nothing — it cannot produce a signature, only test one.

How the public half gets to the verifier is a separate subject with its own page. Key sets, kid, rotation, caching, discovery — none of it is repeated here.

The signature covers the encoded text, not the decoded objects. That is why a verifier must check the bytes it received rather than re-serialising the JSON it parsed — two different encodings of the same object produce two different signatures, and only one of them is the one that was signed.

3A JWT is signed. It is not encrypted.

4The claims that carry weight

  
Values decoded from the real token. Most of these are required for an OAuth 2.0 access token by RFC 9068 §2.2. Two of them are worth more attention than they usually get.


  


  

    Note what is not here: a user. With no resource owner in the flow, sub identifies the calling application itself — RFC 9068 §2.2 says so explicitly. A token from this grant does not represent a person, and any code that assumes sub is a user account will be wrong the first time it meets one.
  






  
5The signing key does not have to be stored anywhere

  
Worth stating because it reframes the question. Key custody is usually discussed as "which vault" — but a keypair generated in memory at startup and never written to disk is a legitimate design.


  

    

      
What it costs

      
A restart invalidates every token already issued. At a 60-second lifetime, that is a window of at most one minute in which callers get a rejection and fetch a new token — which they are built to do anyway, because tokens expire on their own.

    

    

      
What it buys

      
Nothing at rest. No key file, no vault entry, no backup containing it, no rotation procedure, and no way to leak it from storage — because there is no storage. Rotation becomes a restart.

    

  


  

    Multiple instances change the answer. Two servers generating their own keypairs publish two different public keys, so the verifier has to be able to hold both — which is precisely what a key set is for, and another reason the key-distribution page is worth reading before deciding this.
  






  
6Where this comes from

  

    
RFC 7518 §3.3 · Digital Signature with RSASSA-PKCS1-v1_5 — RS256 is "RSASSA-PKCS1-v1_5 using SHA-256", and "a key of size 2048 bits or larger MUST be used with these algorithms." Read first-party 2026-08-06.

    
RFC 7519 §3 · JSON Web Token (JWT) — "A JWT is represented as a sequence of URL-safe parts separated by period ('.') characters. Each part contains a base64url-encoded value."

    
RFC 9068 §2.2 · Data Structure — the required claims iss, exp, aud, sub, client_id, iat, jti; and for grants with no resource owner, sub "SHOULD correspond to an identifier the authorization server uses to indicate the client application."

    
RFC 9068 §2.1 · Header — typ is at+jwt, declaring this is an access token and not some other JWT. "JWT access tokens MUST NOT use 'none' as the signing algorithm."

    
RFC 9700 §2.3 (BCP 240) · Access Token Privilege Restriction — "access tokens SHOULD be audience-restricted to a specific resource server or, if that is not feasible, to a small set of resource servers."

    
ours, not a spec
The 60-second lifetime, the in-memory-keypair option and the "would you put it in a log line" test are our own judgement calls. No RFC sets a token lifetime.
