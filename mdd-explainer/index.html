02The thing AI broke

Same question, same model, three times. Ask again and you get three different correct answers — that is the whole problem, so the button is here rather than a claim you have to take on trust.

one prompt
"How long do I have to return an item?"
✓ correctrun 1
"You've got 365 days to return any item."
✓ correctrun 2
"Our return window is a full year — 365 days from purchase."
✓ correctrun 3
"Returns are accepted for up to 365 days. Happy to help!"
✗ The old assertion is now wrong 

    
You wrote down one exact sentence as the right answer. The assistant said the same thing three different ways, so all three get marked wrong.

    Three correct answers. Three failures. The test is broken, not the software.
  

  

    ✓ What we actually want to know
    

    
Ask instead: did it get the fact across? All three did — so all three pass.

    We never cared about the exact string. We cared about the behavior. Measure that.
  






03But we've solved this before


Not a new problem. Two moves exist; one works for an LLM.




  

    
Door A not viable

    
Make it deterministic

    
Pin temperature to 0, fix the seed, freeze the model. Force one answer so exact-match works again.

    
It still drifts anyway — and even if it didn't, you'd be pinning one frozen string instead of testing that it behaves well across the variation real users see. Testing the wrong thing perfectly.

  

  

    
Door B this is the way

    
Move to a metric-based model

    
Score the behavior of the output, over a dataset big enough that the average is stable: "satisfied 88% of the time."

    
Exactly how we already test noisy systems — sensors, classifiers, flaky calls. That's MDD.

  






04What MDD actually is


The loop is small. The discipline is in doing it before you build, the same way TDD makes you write the test first.




  
1
Define measurements
Decide the metrics that capture "good" for this app — correctness, faithfulness, retrieval, refusal, tone.

  
2
Score each run
Each metric scores one run — usually a value between 0 and 1. One run, one score per metric.

  
3
Run over a dataset
Run every test case in the golden set. Enough of them that one fluke can't swing the result.

  
4
Get a percentage
Average the per-run scores. Now "faithful" is a number you can track, compare, and gate a release on.

  

    
  






05It starts exactly like TDD: the tests come first


You define the tests up front, exactly as TDD taught you. Here those tests are the golden dataset.




  

    
What it is

    
At least ~10 input → expected-output pairs — the ground truths for how the application should behave. You don't write them alone: you collaborate with the subject-matter experts on the application, the people who actually know what "right" looks like.

  

  

    
The one rule

    
Each expected output must be verified as what the human expert would actually do or respond in that scenario, given those inputs. If a human aced this exam, you'd trust them to do the job — that's your ground truth.

  





The ground truth can be wrong too. If the expert phrases an answer differently from the app and the phrasing doesn't matter, rewriting the ground truth to match is a valid fix: you're correcting the measuring stick. Rewriting it to hide a factual miss is not.


Someone has to own "correct". Right on the facts, or right on the facts and the sources behind them? Settle it before the scores mean anything.



"Output" is not just a chat reply. In classic testing the expected output is a return value. Here it can be of any shape — whatever the system actually produces in the real scenario:



  
A responseplain generated text the assistant returns

  
An action takena booking made, a ticket filed, a record updated

  
A tool calledthe right function invoked with the right args

  
A search madethe query it chose to run against the corpus

  
A trajectorya full multi-step path of reasoning + actions






  Code coverage→
  Dataset coverage. The question you used to ask of your lines, you now ask of your set: does it represent the scenarios people actually turn up with? A suite built from one kind of question only tells you about one kind of question.

08Deep dive: how a metric actually works


Zoom into a single run. Same test case throughout, five different answers the app might have given — switch between them and watch the three metrics disagree.




  Grade this run…
  





  
0Two objects, and only one of them can be graded

  







  
  
  





  
the answer↔the ground truth

  
Answer Correctness — did the answer carry the facts the expert said it should? It never looks at the context.

  

    
1Decompose both sides, then classify

    
“Decompose” just means breaking each side into one-fact sentences. It is the step that lets “you have 365 days” and “returns are accepted for a year” count as the same fact. Compare wording and they differ; compare facts and they match.



    

  

  

    
2Do the math — no model, just counting

    

  






  
the answer→the context

  
Faithfulness — is it making things up? The fraction of the answer’s claims the retrieved context actually backs up. Correctness asks “did it match the expert?”; faithfulness asks “could it have known that?”

  

    
1Check every claim against the context

    
Faithfulness never looks at the ground truth. It only asks whether the answer stayed inside the documents it was given — which is why it catches inventions that Answer Correctness waves through.



    

  

  

    
2Divide  

    

    
Count the claims the answer made. Count how many the sources actually back up. Divide. That fraction is the score.

    

  






  
the ground truth→the context

  
Context Recall asks whether the app could possibly have answered: of the facts the expert’s answer needed, how many were actually in what came back? It is the same machine as Faithfulness, fed the other document.

  

    
1Check each required fact against the context

09"Wait — an LLM judging an LLM?!"


The objection every room raises — and a misunderstanding of what the judge is asked to do.




  

    
✗ The fear — and the question behind it

    
If LLMs are unreliable, using one to grade another just stacks unreliability on unreliability. Garbage judging garbage. That fear pictures the judge being asked…

    
"Here's an answer. Is it good? Rate it 1–10."

    
Subjective, unbounded, no single right answer — you'll get a different number every run. It is a bad question. We never ask it.

  

  

    
✓ The reality — what it is actually asked

    
"Unreliable" is not a property of the model, it is a property of the question you hand it. The judge only ever gets questions like…

    
"List the standalone statements in this answer."
"Which of these appear in this context?"

    
Two closed reading tasks with structured answers, at temperature 0. A capable model answers those the same way essentially every time — then code turns the result into a number.

  








  Call 1 and call 2 are the two prompts from the
  deep dive above — decompose the text into
  one-fact sentences, then locate those facts in another document. That is the entire job. Every number on
  this page is arithmetic done in code on the output of those two questions.





Different model = no bias. Best practice is to make the judge a different (often adversarial) model than the one under test, so it can't grade its own homework — no shared blind spots, no self-flattery.





  

    

      One run tells you almost nothing. Ten tell you something.
      A single run's Faithfulness lands anywhere across the scale — same system, same judge. Average ten and the swing shrinks by roughly a factor of √10. Roll it a few times and compare the two bands: that ratio, not any one number, is why a metric is reported over a set. It is also why ~10 is a floor rather than a target — 40 test cases would halve the wobble again. Anthropic argue the same thing more formally in a statistical approach to model evaluations: report the standard error, not just the number.

11Where this comes from







  
Testing never went away. We just stopped asking "does it equal this exact string?" and started asking "how often does it behave the way we agreed it should?" — and let a handful of metrics anyone can follow, charted on a graph, answer it for us.
